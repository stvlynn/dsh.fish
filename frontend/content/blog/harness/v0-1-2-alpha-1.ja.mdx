こんな場面を想像してみてください。DeepSeek Harness を [v0.1.2-alpha.1](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.2-alpha.1)（2026 年 8 月 27 日公開、タグ `dsh-v0.1.2-alpha.1`）に更新し、いつものヘッドレス自動化スクリプトを実行すると、ターミナルに何も表示されなくなります。10 秒、20 秒と過ぎ、「フリーズしたか？」と `Ctrl+C` に手を伸ばしかけた瞬間、完成した最終回答だけが一気に出力されます。

フリーズしていたわけではありません。`dsh-v0.1.2-alpha.1` から、**人間が読む進捗ログ**と**プログラムが処理する最終出力**が明確に分離されたのです。このプレリリースでは、セッションの起動方法、サブエージェントのモデル選択、そして API リクエストに乗るプラグイン情報まで、4 つの大きな境界が一斉に整理されました。

普段 `npx @deepseek-ai/dsh web` を使っている方も、プラグインを作っている方も、手元のターミナルから通信の裏側まで順番に見ていきましょう。

![Harness v0.1.2 が request metadata と headless process output を分離する流れ。](/blog/diagrams/harness-request-path.svg)

## なぜスクリプトが静かになったのか：`stderr` と `stdout` の分離

まずは先ほどの「画面に何も出ない」現象から紐解きましょう。これは自動化スクリプトを書く人が必ずぶつかっていた問題を解決する変更です。

以前のビルドでは、ヘッドレス実行時のツール呼び出しログも、途中の進捗も、最後の回答も、すべて標準出力（`stdout`）に混ざって流れていました。そのため出力を `jq` にパイプしたりファイルに保存したりすると、余計なログを正規表現で削る羽目になっていたのです。

`dsh-v0.1.2-alpha.1` では、2 つのストリームの役割がはっきりと分かれました。

- **`stderr`（標準エラー出力）** には、実行中の進捗やツールトレースがリアルタイムで流れます。
- **`stdout`（標準出力）** はターンが終わるまで沈黙を守り、最後に**最終結果だけ**を出力します。

これによって、標準的なリダイレクトだけで「機械が読める綺麗な結果」と「人間が見る進捗ログ」を同時に扱えるようになりました。

```bash
dsh --profile <profile-name> run "your task" >result.txt 2>progress.log
```

## サブエージェントが親の「重いモデル」をそのまま引き継がなくて済むように

出力が整理されると、次に気になるのは複数ステップのタスクにおけるコストと速度です。

これまでは、メインのエージェントが補助用のサブエージェント（たとえば特定のディレクトリを検索する、テストログを要約するなど）を起動すると、無条件で親セッションと同じモデルが使われていました。親が高コストな推論モデルを使っていると、ちょっとした下調べまで同じ料金と待ち時間を払っていたわけです。

`v0.1.2-alpha.1` では、親が持つ認証の範囲内でサブエージェントごとにモデルを選べるようになりました。

1. **サブエージェントごとのモデル選択：** 親エージェントは、自身が許可されているプロバイダーと認証情報の範囲内で、サブエージェントのプロバイダー・モデル・推論強度（reasoning effort）を指定できます。
2. **起動時の出力長制限：** サブエージェントを起動する側は、モデルや推論強度に加えて**最大出力長（maximum output length）**を設定できます。
3. **Claude Code と Codex の個別モデル設定：** Claude Code や Codex をサブエージェントとして使う場合、親のモデルを引き継ぐのではなく、あらかじめ設定された専用モデルで動くようになりました。

`dsh.fish` で Profile を公開・利用する際も、「親は深い推論モデル、子タスクは高速な Flash モデル」という役割分担を Profile にそのまま書き込めます。

## プラグインを有効にすると、どんな情報がリクエストに乗るのか

カタログから Bundle を Profile に入れたとき、モデル提供側には何が見えるのでしょうか？

`dsh-v0.1.2-alpha.1` から、**公式 DeepSeek アダプター**を使っている場合、送信される API リクエストに**有効になっているすべてのプラグインのパッケージ名とバージョン**が付与されるようになりました。

押さえておきたいポイントは 2 つあります。

- **プラグイン情報ヘッダーはデフォルト有効ですが、オフにできます。** デプロイ環境の方針に応じて無効化が可能です。
- **セッションログの増分アップロードはオプトイン（デフォルト無効）です。** 同じ通信経路でセッションログを送る仕組みも追加されましたが、明示的に有効化しない限り送信されません（`dsh.fish` のインストール計画がこの設定をオンにすることもありません）。

また、プラグイン開発者向けに、**Models 設定ページに独自のサインイン UI（OAuth やトークンログイン）を追加できるフック**も導入されました。

## Python SDK と ACP も同じ Profile の玄関を通る

ブラウザ UI（`dsh web`）だけでなく、**Python SDK や ACP から起動する場合もすべて `dsh` Profile を通る**ようになりました。

- **Python SDK** のランタイムに **Windows x64** 向けのビルドが追加されました。
- **ACP（Agent Client Protocol）** は部分的なスタブを卒業し、セッション制御、モデル設定、MCP、権限、キャンセルまで一通りの制御が揃いました。

## アップグレード前に確認すべき 4 つの破壊的変更

古い前提のままこのバージョンに上げると、一見原因が分かりにくいエラーに遭遇します。移行前に次の 4 点を確認してください。

| `v0.1.2-alpha.1` 以前の前提 | 新しい挙動 | 対応方法 |
| --- | --- | --- |
| プラグインが `ApiProxy` をインポートしている | **読み込めません。** `@Remote` ゲートウェイへの移行が完了しました。 | `ApiProxy` の呼び出しを `@Remote` ゲートウェイに書き換えてください。 |
| 設定や README で **Code Mode** と呼んでいる | **PTC mode**（`run_code`）に改칭されました（既存セッションの読み込みは可能）。 | プリセット名やドキュメントの表記を PTC mode に更新してください。 |
| 公開 URL への `WebFetch` が毎回承認を求める | 公開ネットワークへの `WebFetch` が **デフォルトでオン**（SSRF 保護付き）になりました。 | 公開 URL へのアクセス制限を承認プロンプトに頼らないようにしてください。 |
| ネットワーク越しに `dsh web` へトークンなしで接続する | リモートから Web UI を開くには **起動 URL のワンタイムトークン** が必須になりました。 | ローカル（`127.0.0.1`）は従来通りですが、別端末から開く際はトークン付き URL を使ってください。 |

## UI・ストレージの改善と Safety Notice（安全に関する注意）

日々の使い勝手や安定性も大きく改善されています。

- **会話画面とログ保存の軽量化：** 回答完了後に途中の処理詳細や System プロンプトが自動で折りたたまれ、回答末尾でトークン数を開閉できるようになりました。ログのディスク使用量も削減され、末尾が切れたログは警告付きで自動修復されます。
- **永続シェルの安定化：** macOS/Linux で永続 PowerShell が早く起動しすぎる問題、Linux の永続 Bash でパイプライン途中が空になる問題、macOS で Bash が大量の子プロセスを生んだ際に固まる問題が修正されました。

最後に、このタグで更新された **Safety Notice** を必ず確認してください。DeepSeek Harness は**セキュリティ監査を受けておらず**、サンドボックスや承認・権限の仕組みは**完全な隔離を保証しない**と公式に明記されました。公開 `WebFetch` がデフォルト有効になったのは利便性のためであり、サンドボックスが強化されたという意味ではありません。引き続き機密情報はワークスペースの外に置き、`danger-full-access` の扱いには十分注意してください。
