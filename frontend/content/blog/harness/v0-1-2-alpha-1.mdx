Picture this: you update DeepSeek Harness to [v0.1.2-alpha.1](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.2-alpha.1) (published 27 August 2026 under the git tag `dsh-v0.1.2-alpha.1`), run your usual headless automation script, and stare at a completely blank terminal. Ten seconds pass. Twenty seconds pass. Just as you reach for `Ctrl+C` thinking the process hung, the entire finished answer prints at once.

Nothing hung. Instead, `dsh-v0.1.2-alpha.1` drew a clean line between **human progress logs** and **machine-readable output**—one of four structural shifts in this pre-release that reshaped how sessions start, how subagents pick their models, and what metadata travels over the wire.

If you run `npx @deepseek-ai/dsh web` or build plugins for the catalog, here is how those pieces fit together from the terminal all the way to the API request.

![Harness v0.1.2 separates request metadata from headless process output.](/blog/diagrams/harness-request-path.svg)

## Why your terminal script went quiet: `stderr` vs. `stdout`

Let us start with that "blank terminal" surprise, because it solves a headache every automation author has hit.

In earlier builds, running DeepSeek Harness in headless mode mixed everything into standard output (`stdout`): tool call logs, intermediate progress lines, and the final answer. If you piped `dsh` into `jq` or saved the output to a file, you had to write brittle regexes to strip out the tool chatter first.

Starting in `dsh-v0.1.2-alpha.1`, headless runs split the two streams cleanly:

- **`stderr` (standard error)** streams live progress events and tool traces while the agent works.
- **`stdout` (standard output)** stays completely silent until the turn finishes, then prints **only the final result**.

That means a pipeline can now capture clean output in one file while watching live diagnostics in another:

```bash
dsh --profile <profile-name> run "your task" >result.txt 2>progress.log
```

## Subagents no longer have to clone a heavyweight parent model

Once your scripts are clean, the next bottleneck you notice in multi-step tasks is cost and latency.

Previously, when a main agent spawned a helper subagent (for example, to search a directory or summarize a test log), the child automatically inherited the parent session's model. If your main session was running a heavy reasoning configuration, every tiny helper task paid that same latency and token price.

In `v0.1.2-alpha.1`, subagents gained independent model selection within the parent's authorization boundary:

1. **Dynamic choice:** A parent agent can pick the provider, model, and reasoning effort for a subagent using any credentials the parent already has permission to use.
2. **Spawn-time limits:** Callers that launch a subagent can specify provider, model, reasoning effort, and a **maximum output length** cap.
3. **Dedicated slots for Claude Code and Codex:** If you mount Claude Code or Codex as subagent bundles, they now read their own configured model instead of blindly copying the parent session's model slot.

For profile authors on `dsh.fish`, this is a practical upgrade: you can pair a deep-reasoning orchestrator with fast, inexpensive worker subagents inside a single profile configuration.

## What leaves your machine when plugins are enabled

When you install a bundle from a catalog into a profile, does the model provider know which plugins are active?

Starting with `dsh-v0.1.2-alpha.1`, when you use the **official DeepSeek adapter**, outbound API requests include a metadata header listing the **package name and version of every enabled plugin** in that profile.

Two design details matter here:

- **The plugin header is on by default, but configurable.** Self-hosted or privacy-sensitive deployments can turn the metadata header off.
- **Session-log streaming is strictly opt-in.** A second channel can upload incremental session logs along with official requests, but it stays **off** unless you explicitly enable it (`dsh.fish` install plans never turn this flag on).

For plugin authors, there is also a new UI hook: plugins can now **register a custom provider sign-in control directly on the Models settings page**, placing an OAuth button or token login card right beside the built-in providers.

## One front door for Python SDK and ACP

If you only use the browser UI (`dsh web`), you were already using profiles. What changed in `v0.1.2-alpha.1` is that **every other entry point now walks through the same front door**:

- **Python SDK** sessions now boot through a `dsh` Profile, and this release adds the prebuilt **Windows x64** runtime wheel.
- **ACP (Agent Client Protocol)** graduated from an early stub to a complete preview surface: session lifecycle (`session/new`, `session/resume`, `session/close`), model settings, MCP mounts, permission prompts, and cancellation are all wired up.

## Four breaking changes to check before upgrading

Because several old seams were removed at once, upgrading an older profile or script without checking these four items will cause errors that look unrelated at first glance:

| Old assumption before `v0.1.2-alpha.1` | What happens now | How to update your profile or script |
| --- | --- | --- |
| Importing `ApiProxy` in a plugin | **Fails to load.** Migration to the `@Remote` gateway is complete. | Replace `ApiProxy` imports with the `@Remote` gateway APIs. |
| Preset or docs naming **Code Mode** | Renamed to **PTC mode** (`run_code`). Old session logs still open cleanly. | Update preset configs and documentation from Code Mode to PTC mode. |
| Public `WebFetch` asks before every URL | **On by default** for public URLs (with built-in SSRF protection). | Do not rely on the approval prompt as a gate for public HTTP fetches. |
| Exposing `dsh web` across a LAN without a token | Network-bound Web UI now requires the **one-time launch token** in the URL. | Copy the full tokenized launch URL when connecting from another device; local loopback (`127.0.0.1`) is unchanged. |

## Quality-of-life improvements and the updated Safety Notice

Alongside the architectural shifts, daily sessions feel noticeably cleaner:

- **Lighter conversation UI and storage:** Completed answers fold the intermediate process details and System prompt by default, display expandable token counts at the bottom of each reply, and let you drag the conversation column width. On disk, session records take less space and automatically repair truncated log tails with a clear warning.
- **Shell stability across OSes:** Persistent PowerShell on macOS and Linux no longer fires prematurely, persistent Bash on Linux no longer drops output mid-pipeline, and macOS hosts no longer stall during rapid Bash process bursts.

Finally, read the updated **Safety Notice** in this tag carefully: DeepSeek Harness explicitly states that the runtime **has not been security-audited**, and that sandboxing, approvals, and permissions **do not guarantee complete isolation**. Turning public `WebFetch` on by default is a convenience change, not a claim that the sandbox became hardened. Keep sensitive credentials outside your workspace and treat `danger-full-access` with the caution its name implies.
