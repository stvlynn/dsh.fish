设想这样一个场景：你把 DeepSeek Harness 升级到了 [v0.1.2-alpha.1](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.2-alpha.1)（发布于 2026 年 8 月 27 日，Git 标签为 `dsh-v0.1.2-alpha.1`），像往常一样运行自动化脚本，结果终端屏幕一片空白。十秒过去了，二十秒过去了，正当以为进程卡死准备按 `Ctrl+C` 时，完整的最终回答突然一次性打印了出来。

进程并没有卡死。相反，`dsh-v0.1.2-alpha.1` 首次在**给人看的进度日志**与**给机器读的结果输出**之间画下了一条干净的分界线。这也是本次预发布版四大结构性演进之一：从会话如何启动、子智能体（Subagent）如何选模型，到请求头里携带哪些插件信息，都在这一版完成了定型。

如果你平时使用 `npx @deepseek-ai/dsh web` 或为目录开发插件，不妨跟着我们从终端表现一路追查到底层协议。

![Harness v0.1.2 将请求 metadata 与 headless process output 分开。](/blog/diagrams/harness-request-path.svg)

## 为什么脚本突然“安静”了：`stderr` 与 `stdout` 的彻底分流

先从刚才那个“终端空白”的现象说起，因为它解决了一个长期困扰自动化开发者的痛点。

在早期版本中，无头模式（Headless）会把所有内容混在标准输出（`stdout`）里打印：工具调用轨迹、中间思考进度、以及最终答案全挤在一条流里。如果你想把 `dsh` 的输出通过管道传给 `jq`，就不得不先写一堆脆弱的正则表达式去过滤中间日志。

从 `dsh-v0.1.2-alpha.1` 开始，无头运行将两条输出流彻底分开：

- **`stderr`（标准错误流，文件描述符 2）** 实时输出执行进度与工具调用轨迹。
- **`stdout`（标准输出流，文件描述符 1）** 在任务完成前保持绝对安静，最后**只打印最终结果**。

这意味着你现在可以用一行标准重定向，同时拿到干净的机器结果和实时进度日志：

```bash
dsh --profile <profile-name> run "your task" >result.txt 2>progress.log
```

## 子智能体终于不必“被迫继承”昂贵的父模型

解决了输出解析问题后，多步任务里的下一个瓶颈往往是成本与延迟。

在此之前，当主智能体派生一个子智能体（比如去翻阅某个子目录或汇总测试日志）时，子智能体默认直接克隆父会话的模型槽位。如果你的主会话正在跑高强度的重型推理模型，哪怕是打杂的小任务也会按最高规格消耗 Token 和等待时间。

在 `v0.1.2-alpha.1` 中，子智能体获得了独立的模型选择权：

1. **在父级授权范围内按需选型：** 主智能体可以在自己已获授权的供应商与密钥范围内，为子智能体指定不同的供应商、模型和推理强度（reasoning effort）。
2. **启动时设置输出上限：** 调用方在派生子智能体时，可以直接指定供应商、模型、推理强度以及**最大输出长度（maximum output length）**。
3. **Claude Code 与 Codex 子智能体支持固定模型：** 如果你在 Profile 中挂载了 Claude Code 或 Codex 作为子智能体，它们现在会读取各自配置的专属模型，而不再盲目继承父会话模型。

对于 `dsh.fish` 上的配置作者来说，这意味着你可以在同一个 Profile 里实现“主模型深度规划 + 轻量 Flash 子模型并发执行”的高效组合。

## 当插件启用时，哪些信息会随请求发出？

当你把目录里的扩展包（Bundle）安装进 Profile 后，模型服务商知道你加载了哪些插件吗？

从 `dsh-v0.1.2-alpha.1` 起，在使用**官方 DeepSeek 适配器**时，发出的 API 请求默认会附带当前 Profile 中**所有已启用插件的包名与版本号**。

这里有两个关键的边界设计：

- **插件标识头默认开启，但允许关闭。** 私有化或注重边界的部署环境可以在配置中关闭该请求头。
- **增量会话日志上传默认关闭（Opt-in）。** 同一通道还支持随请求流式上传增量会话日志，但默认保持**关闭**，除非你显式开启（`dsh.fish` 生成的安装计划绝不会开启此开关）。

此外，插件作者还获得了一个实用的界面扩展点：插件现在可以**在“设置 → 模型（Models）”页面直接注册自定义的登录控件**，把自己的 OAuth 或 Token 登录卡片与内置供应商并排展示。

## Python SDK 与 ACP 走入同一扇大门

如果你只用浏览器界面（`dsh web`），你其实已经在用 Profile 了。`v0.1.2-alpha.1` 的重要变化在于，**所有其他调用方式也全部统一到了 Profile 体系下**：

- **Python SDK** 现在同样通过 `dsh` Profile 启动，并且本版本新增了 **Windows x64** 预编译运行时轮子（wheel）。
- **ACP（Agent Client Protocol）** 不再是半成品桩代码：会话控制、模型设置、MCP 挂载、权限审批和取消操作已全部补齐。如果你之前因为缺少某个控制接口而搁置了 ACP 集成，现在正是重新联调的节点。

## 升级前必查的四项不兼容变更

由于本版本一次性清理了多处旧接口，在迁移旧 Profile 或脚本前，请务必核对以下四项假设：

| `v0.1.2-alpha.1` 之前的旧假设 | 现在的实际行为 | 迁移与修复方式 |
| --- | --- | --- |
| 插件代码仍然导入 `ApiProxy` | **无法加载。** 已全面迁移至 `@Remote` 网关。 | 将所有 `ApiProxy` 调用替换为 `@Remote` 网关接口。 |
| 预设或文档仍使用 **Code Mode** 名称 | 正式更名为 **PTC mode**（`run_code`），旧会话历史仍可正常读取。 | 将配置与 README 中的 Code Mode 统一更新为 PTC mode。 |
| 公网 `WebFetch` 每次都弹窗请求批准 | 公网 URL 获取**默认开启**（内置 SSRF 防护），不再逐次弹窗。 | 不要再把审批弹窗当作公网 HTTP 请求的拦截阀门。 |
| 跨局域网直接裸连 `dsh web` | 通过网络访问 Web UI 必须在启动链接中携带**一次性令牌（one-time token）**。 | 本机回环（`127.0.0.1`）不受影响；跨机器访问请使用终端打印的带令牌完整 URL。 |

## 界面体验打磨与安全声明（Safety Notice）更新

除了底层协议演进，日常使用体验也有不少扎实的改进：

- **更清爽的会话界面与更省空间的日志：** 每条已完成的回答默认折叠中间过程细节与 System 提示词，回答末尾提供可展开的 Token 统计，并支持拖拽调整对话列宽。磁盘上的会话记录体积更小，遇到截断的日志尾部时会自动修复并指明对应的会话。
- **跨平台持久终端修复：** 修复了 macOS/Linux 上持久 PowerShell 过早启动、Linux 上持久 Bash 在管道中途返回空输出、以及 macOS 在 Bash 瞬间派生大量子进程时卡死的问题。

最后，请留意本版本更新的 **Safety Notice（安全声明）**：官方明确写道，DeepSeek Harness **尚未经过安全审计**，沙箱、审批与权限机制**不保证绝对隔离**。公网 `WebFetch` 默认开启只是为了减少重复点击，绝不代表沙箱边界变得坚不可摧。请继续将敏感凭证保存在工作区之外，并谨慎对待 `danger-full-access`。
