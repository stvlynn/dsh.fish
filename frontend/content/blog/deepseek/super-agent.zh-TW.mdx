我平時在電腦上同時開四五個 Agent 工作階段，基本就是極限了。再多開幾個視窗，切來切去，很快就會搞混剛才在哪個工作階段裡交代過哪件事，最後乾脆所有視窗都停下來等我回話。

10 月 31 日，DeepSeek Harness 團隊發了一篇《[Super-agent 設計探索：邁向更自主的 Agent 系統](https://telegra.ph/Super-agent-%E8%AE%BE%E8%AE%A1%E6%8E%A2%E7%B4%A2%E8%BF%88%E5%90%91%E6%9B%B4%E8%87%AA%E4%B8%BB%E7%9A%84-Agent-%E7%B3%BB%E7%BB%9F-10-31)》，裡面給的觀察數字也是 3 到 5 個。文章的說法很直接：單任務的上限看模型能力，多任務的上限看人的注意力。現在卡住整個系統的往往不是 GPU，而是螢幕前那個人腦子裡能同時裝下多少事。

隨文章一起放出來的還有 [`deepseek-ai/dsh-superagent-prototype`](https://github.com/deepseek-ai/dsh-superagent-prototype)，一個打包成 DeepSeek Harness bundle 的研究原型。它可以盯著一個 GitHub 儲存庫或飛書群，把符合條件的請求轉成工單，在各自獨立的工作階段和目錄裡幹完活，最後回到原對話交差（一般是提一個 Pull Request）。儲存庫的 README 把話說得很死：這只是研究程式碼，不是正式產品，公開出來的版本和文章裡寫的內部系統也不完全一樣。

我把文章裡的實驗數據和這個儲存庫的程式碼放在一起翻了一遍。有幾個地方光看文章很容易一帶而過，但對照著程式碼看，挺有意思。

## 文章和原型的模組對照

文章用連續、高效、主動、持久四個詞概括 Super-agent 的目標，下面拆了五個模組。因為在公開原型裡部分命名和文章不太一樣，有的模組乾脆沒放進來，先列一張對照表省得後面串線：

| 文章模組 | 處理的問題 | 公開原型裡的實作 |
| --- | --- | --- |
| 雙層架構（Router / Worker） | 既要持續響應，又要並行幹活 | 一個主 Session（程式碼裡叫 `orchestrator`），每個工單開一個執行器 Session（`worker`） |
| 事件驅動（Trigger / Thread / 訂閱直通） | 主動觸發與路由開銷 | Source → Trigger → Thread → Eval → Ticket，靠 `Subscription` 把訊息分發給工單 |
| 面向人的互動（全雙工、多通道） | 別卡死對話，也別洗版 | 前景 shell 命令跑滿 5 秒自動轉背景；聊天回覆預設一句話，最多 100 詞 |
| 計算、狀態與環境分離 | 重啟恢復與跨裝置 | 跑在獨立的本地 DSH Profile 裡，靠本地狀態目錄和「先落盤、後執行」的佇列扛住處理程序重啟 |
| Watchdog | 異常自愈 | 公開原型的文件和程式碼裡都沒看到這一塊 |

![每一層都只把需要上一層拍板的事情往上送：程式碼層准入過濾、攢批處理的 Router、靠訂閱直通收訊息的 Worker，以及最後只收到一條簡短回覆的人。](/blog/diagrams/super-agent-attention.svg)

## 一、給模型配了 Subagent 工具，它為什麼不用？

第 7.1 節的消融實驗裡有一組挺扎眼的數據。

實驗往系統裡灌了大約 300 條群聊和 CI 訊息，其中真正需要幹活的請求大概 20 條，每組配置跑 5 輪。對照組是大家平時最熟悉的那種用法：單 Session 加一個 Subagent 工具，主工作階段覺得合適就把活派給子代理。

結果在中性提示詞（「Use a subagent for a piece of work when appropriate...」）下，跑了 5 輪，模型呼叫 Subagent 的次數是 **0**。所有活全堆在主工作階段裡自己幹，中途不斷被新湧進來的訊息打斷，p95 完成時間拖到了 29.5 分鐘；而雙層架構的 Super-agent 是 15.7 分鐘。

後來團隊把提示詞改成明確要求「優先委派」，5 輪裡總算有 4 輪派了子代理。但還是有 1 輪，模型覺得手頭這件活很小，順手就自己幹了，結果那一次直接在耗時曲線上拉出一條長尾。

平時常寫提示詞的人大概都遇到過這種脾氣。讓模型派子代理，它得先組織語言把上下文寫清楚，還得等那邊跑完回報；而自己順手跑個命令，在當下這一步看起來省事得多。單看每一次判斷都很合理，但只要主工作階段親自動手幹一件「小活」，後面進來的訊息就全堵在門口了。就像協作式多工裡一個死活不肯讓出 CPU 的執行緒，每段程式碼看著都不長，整個系統卻照樣卡死。

指望靠提示詞勸模型「顧全大局」顯然不太靠譜。文章給出的辦法很乾脆：Router 層只管分發，不幹具體活，甚至可以連 Bash 工具都不給。

翻看原型的程式碼，限制比文章寫得還要死。主 Session 跑在單獨的 `dsh-superagent-router` 預設組下，能用的工具很少；宿主程式碼直接攔掉了 `sleep` 呼叫，shell 超時不允許超過 30 秒，等待背景任務不允許超過 5 秒。

執行器（`dsh-superagent-worker`）那邊也做了類似的處理。文章裡原本講的是用非同步 `start()` / `stop()` 做全雙工 ReAct 迴圈（文章註明這個機制在 DeepSeek Harness 裡已經寫好了，只是還沒預設打開）。公開原型沒走這條路，而是用了一個更粗暴的規則：只要前景 shell 命令跑滿 5 秒沒結束，宿主就自動把它塞進背景任務，讓執行器在下一步立刻騰出手來收新訊息。命令到底該同步跑還是非同步跑，根本不用模型自己拿主意。

## 二、7.2 節壓測表裡少算的一筆帳

再看第 7.2 節的 Router 壓力測試：

| Trigger 到達速率 | 平均 batch | 單次請求耗時 | 單個決定分攤耗時 |
| --- | --- | --- | --- |
| 約 1 條/分鐘 | 1.0 | 2.5 秒 | 6.4 秒 |
| 約 40 條/分鐘 | 2.8 | 3.9 秒 | 1.6 秒 |

訊息湧入的速度漲了 40 倍，平均每個路由決定的耗時反而從 6.4 秒降到了 1.6 秒。文章給出的解釋是：Router 每一步都是長輸入、短輸出，攢在一起的多個 Trigger 放進同一次請求裡，正好在 GPU 的 Prefill 階段平行算完，所以單次請求耗時只從 2.5 秒漲到 3.9 秒。

不過我順手除了一下這幾個數，發現光靠 Prefill 平行對不上帳。

低負載下，單次請求 2.5 秒，做出一個決定要 6.4 秒，相當於每個決定平均要走 2.6 輪模型呼叫。到了高負載，單次請求 3.9 秒，如果一個決定還是得走 2.6 輪，那再怎麼除以 2.8 的平均 batch，分攤下來也得 3.6 秒左右。但表裡實測只有 1.6 秒——算下來每個決定只用了 0.4 輪呼叫，輪數足足少了 6 倍多。

省出來的輪數是哪來的？文章沒細說，我去翻了原型裡路由工具的定義。

原型裡的 `orchestrator_route` 工具，參數直接就是一個陣列，一次呼叫能同時塞進多條 `accept`、`attach`、`stop` 或 `ignore` 決定，每條獨立校驗生效，就算其中一條被打回也不耽誤別的。同時，主 Session 的系統提示詞明確要求：如果有多個候選事件在排隊，那些光看事件卡片就能拍板的，直接打包進同一次 `orchestrator_route` 提交；只有實在拿不準、必須翻上下文的候選，才單獨調讀取工具，而且讀取呼叫要和路由呼叫在同一輪裡並發出去。

要是當初把路由工具設計成「一次呼叫只處理一條訊息」，那哪怕 GPU Prefill 再快，每條訊息也至少得佔一輪工具往返。現在把工具簽名設計成批次的，再配合「同一條 Thread 上同一時間只跑一個 Eval，期間新來的 Trigger 自動歸入下一批」的循序佇列，忙起來的時候連讀上下文和交決定這兩步都合著幹了。這跟資料庫裡的組提交（group commit）或者網路卡的中斷合併是一個路數：平時來一條處理一條，真堵上了就順勢攢成一批走完。

## 三、訂閱直通省下的不是時間

同一組消融實驗裡還有一行數據：把「訂閱直通」（也就是某個工單訂閱了一條 Thread 之後，後續該 Thread 上的新訊息由程式碼直接塞給對應的 Worker，不再經過 Router）關掉。

關掉之後，任務的完成時間和完整版幾乎沒差別。變化的是另外兩個數：Router 需要做的決定多了約 30%，快取讀取的 token 從 2323 萬漲到了 3177 萬，多了 37%。

剛看到這兒的時候我有點意外——既然上一節壓測證明 Router 的吞吐量根本不是瓶頸，關掉直通也沒拖慢任務速度，那費勁做這一層旁路幹什麼？

答案其實在上下文視窗的壽命上。整個系統裡只有 Router 這一個主工作階段一直活著、拿著全域記憶。要是每個工單跟進過程中的討論、CI 報錯、補充說明全都從 Router 眼前過一遍，這些雜訊就會一直墊在它的歷史記錄裡。Token 帳單漲了 37% 還是其次，更麻煩的是主工作階段的上下文視窗很快就會被無關細節塞滿，壓縮得越頻繁，後面的路由判斷就越容易犯糊塗。直通繞開 Router，圖的就是別拿執行過程中的瑣事去污染主工作階段的記憶。

## 四、能看見訊息，不代表能發號施令

把 Agent 放進真實的 GitHub 儲存庫或群聊，最頭疼的其實是雜音和越權。平時我們在群裡聊工作，能看到訊息的人就能插話提要求，聊著聊著話題沾邊了大家就當成一件事處理。但如果讓 Agent 也這麼幹，隨便一條路人評論或者 CI 吐出來的日誌都能把正在幹活的 Worker 帶偏。

原型在領域模型裡把「收訊息」「給權限」和「查背景」硬拆成了三件互不相干的事：

| 概念 | 在原型裡幹什麼 | 明確禁止什麼 |
| --- | --- | --- |
| Subscription（訂閱） | 把 Thread 上的新訊息（包括機器人和 CI 訊息）轉發給訂閱了它的工單 | 不附帶任何執行權限 |
| Mandate（授權） | 記錄接單時的策略版本、權限範圍、強度、命中的規則、發起人身份和來源管道 | 不能擴權；超出原範圍的事必須另開新工單 |
| Correlation（關聯） | 評估時掛一點相關上下文供參考 | 絕不作為路由分發依據 |

這三者裡，`Mandate` 卡得最死。只有接單那一刻能建立它；之後要麼由人主動叫停，要麼在策略檔案更新後因為重新校驗不過關而被系統吊銷。除此之外，工單執行過程中收到的任何訊息、評論或引用的文件，都只是普通的輸入資料，改不動 `Mandate` 裡的半個字。

翻看主 Session 的提示詞，還有兩條挺有意思的死規矩：

一條是「寧可重開，不可亂掛」。主 Session 只有在訊息**明確點名**某個現有工單時，才允許把它 `attach` 上去——比如直接引用了那個工單的 PR、Issue、源訊息或確認回覆，或者聊的是剛剛改完的東西且全場只有一個工單對得上。光是「話題差不多」一律不准往上掛。提示詞裡解釋得很實在：不小心重複開了一張工單，關掉就是了；可要是把不相干的訊息掛錯了工單，那個工單就會自動訂閱整條 Thread，以後那條線上的所有動靜都會源源不斷地往裡灌。

另一條是不准 Router 當「二傳手」。主 Session 把請求轉給執行器時，只准傳原始 Trigger 的引用 ID 和必要的路由資訊，嚴禁把別人的一句話需求擴寫成工作計劃，也不准自己往上添驗收標準或檢查清單。具體要幹什麼，執行器自己拿 ID 回原始訊息裡看。這跟文章 3.3 節講的「鏈式召回」（用物件 ID 串起上下文，需要時再展開原文）是一個思路——Router 每替人總結一次，資訊就走樣一點，還不如直接傳引用。

文章的第 8.4 節把安全與隱私歸為「開放問題」，而公開原型專門用了一篇 `002-authorization.md` 來落地這套機制。裡面還給主動規則加了個預設 `observe`（觀察）模式：評估結果覺得「應該接單」時，先只記一筆日誌、不真動手，等團隊看過日誌覺得靠譜了再切到 `auto`。

說到底，不管是防提示詞注入，還是第一節裡防模型大包大攬，原型的做法其實都一樣：別指望模型光靠讀一段文字警告就能管住自己。在原型的提示詞優先順序表裡，排第一的是「工具和宿主程式碼強制執行的事實」，排在最末位的才是外部文字——文件裡直接寫著，外部文字只是資料，永遠改不了規則和授權。

## 五、不再手動管 Session 之後，介面上還剩什麼？

文章裡提了一個挺準的判斷：現在大家習慣手動建 Session、切 Session，很大程度上只是因為底層 LLM API 長這樣，介面順著 API 做了而已。

如果把 Session 藏到幕後，人平時盯著看的單位就變成了 `Ticket`（工單）。在原型的領域模型裡，工單的狀態是故意跟底層的 DSH Session 脫鉤的——因為同一張工單中途可能會失敗重試、處理程序重啟後恢復，或者先後換好幾個執行器接手（對應多個 `Assignment`）。對提需求的人來說這只是一件事，底下到底跑了幾個工作階段並不重要。

要做到這一點，工單就得扛得住處理程序重啟。原型裡凡是拍板之後要做的動作——把候選事件轉給主 Session、拉起 Assignment、投遞輸入、往外發回覆——全都先寫進本地狀態目錄，再非同步執行，失敗了就按退避策略重試。萬一處理程序掛了重啟，剛才跑了一半的 Assignment 會帶著一段恢復提示重新拉起來，叮囑執行器在重新執行任何外部操作之前，先去翻翻本地工作目錄、`git log` 和 GitHub 上的狀態。畢竟工作階段記憶體丟了也就丟了，之前評論發沒發出去、PR 建沒建好，去 GitHub 上看一眼就知道，沒必要傻乎乎地再發一遍。

原型的狀態面板也順著這個思路做了減法。工單狀態從上往下排，最頂上幾欄全是以 `person / …` 開頭的項：輸入投遞失敗、等人類回話、等人類 Review PR、卡住或者徹底失敗。正常在背景跑著的工單乾脆不往眼前湊。文章第 8.2 節還在討論脫離 Session 之後人機互動該長什麼樣，原型給出的方案其實就是個待辦佇列——按「哪件事正卡在人身上」來排優先順序。

## 一層層往下擋雜訊

把上面這些零碎的機制拼到一起，其實每一層都在幹同一件事——替上一層擋掉不需要它操心的資訊：

| 層級 | 最怕被什麼拖垮 | 原型裡的擋法 |
| --- | --- | --- |
| 人 | 群訊息洗版、不停被追問、自己記一堆工作階段的上下文 | 只有 Router 對外說話；聊天回覆預設一句話、最多 100 詞；接單確認只發一次；面板上只列卡在人身上的工單 |
| Router（主 Session） | 上下文被無關對話塞滿，或者在某一步卡住導致全域排隊 | 進模型前先過程式碼准入過濾；已訂閱的 Thread 直接走旁路送給 Worker；路由備註限制在 30 詞以內；平時不讀程式碼也不查日誌 |
| Worker（執行器 Session） | 一條長訊息把上下文撐爆，或者被一條慢命令卡死 | Inline & Spill：事件卡片超過 600 字元就截斷並留個續讀指標；前景命令跑滿 5 秒自動轉背景 |

原型文件 `000-philosophy.md` 的第一條寫得很白：「Take as little human attention as possible, and give as much value as possible.」

文章裡雖然搬出了 Fast Path / Slow Path、批處理、快取、投機執行、存算分離等一串系統工程概念，但落到程式碼裡，核心都是在省「注意力」——不管是人的注意力，還是模型有限的上下文視窗。人盯不住那麼多工作階段，就加一層 Router 替人看門；Router 的全域上下文金貴，就用訂閱直通和 Worker 把具體幹活的過程剝出去；Worker 自己的視窗也經不起長日誌折騰，就靠 600 字元截斷（Inline & Spill）和子代理再擋一層。

人腦同時能顧得上的事情還是只有 3 到 5 件，Super-agent 也沒法讓人長出三頭六臂。它真正改變的是佔住這 3 到 5 個坑位的東西：以前是你得自己記著前因後果的 3 到 5 個聊天視窗，現在變成 3 到 5 個已經跑出結果、只等你點個頭或者批個 PR 的工單。

## 順帶聊聊外掛生態與試用提醒

作為一個維護 DeepSeek Harness 外掛目錄的網站，我翻 `dsh-superagent-prototype` 時最先看的其實是它的目錄結構。

它本身就是一個標準的 DeepSeek Harness bundle：根目錄下一份 `cordis.patch.yml` 把外掛掛進去，再給主 Session 和執行器各配一套預設組，Harness 核心程式碼一行沒動。之前我們在《[一切皆外掛](/blog/notes/everything-is-a-plugin)》裡聊過這套外掛機制的邊界，現在連官方團隊探索 Super-agent 也是直接打成一個 Profile 擴充套件來跑。

而且如果你讀過前幾天那篇《[DeepSeek Bot 生態全景](/blog/notes/deepseek-bot-ecosystem)》，看到這兒大概已經會心一笑了。社群專案 Tobs（`@botharness/tobs`）為了解決群聊收件匣卡死的問題，自己摸索出來的也是「常駐 Orchestrator 工作階段 + 背景 Assignment 工作階段」的雙層結構，連命名都撞了一半。只要你真想讓 Agent 在群聊裡長期掛著幹活，最後往往都會被逼到同一條架構路子上去。

最後提醒一句：如果你想在自己機器上跑一下這個原型，先看一眼它的權限配置。按儲存庫部署文件的說明，主 Session 和執行器兩套預設組預設都開了 `danger-full-access`，直接以當前系統使用者的身份免核准跑命令；裡面帶的帳號包裝腳本只是切換預設憑證，並沒有做處理程序級沙箱隔離。真要掛到群裡或者儲存庫上跑，最好按文件建議單獨建一個只放 Agent 憑證的受限系統使用者，先把允許觸發的名單收緊，主動規則留在預設的 `observe` 模式跑幾天，看看日誌裡它打算接哪些單，心裡有底了再切到 `auto`。
