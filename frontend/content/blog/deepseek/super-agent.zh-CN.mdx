我平时在电脑上同时开四五个 Agent 会话，基本就是极限了。再多开几个窗口，切来切去，很快就会搞混刚才在哪个会话里交代过哪件事，最后干脆所有窗口都停下来等我回话。

10 月 31 日，DeepSeek Harness 团队发了一篇《[Super-agent 设计探索：迈向更自主的 Agent 系统](https://telegra.ph/Super-agent-%E8%AE%BE%E8%AE%A1%E6%8E%A2%E7%B4%A2%E8%BF%88%E5%90%91%E6%9B%B4%E8%87%AA%E4%B8%BB%E7%9A%84-Agent-%E7%B3%BB%E7%BB%9F-10-31)》，里面给的观察数字也是 3 到 5 个。文章的说法很直接：单任务的上限看模型能力，多任务的上限看人的注意力。现在卡住整个系统的往往不是 GPU，而是屏幕前那个人脑子里能同时装下多少事。

随文章一起放出来的还有 [`deepseek-ai/dsh-superagent-prototype`](https://github.com/deepseek-ai/dsh-superagent-prototype)，一个打包成 DeepSeek Harness bundle 的研究原型。它可以盯着一个 GitHub 仓库或飞书群，把符合条件的请求转成工单，在各自独立的会话和目录里干完活，最后回到原对话交差（一般是提一个 Pull Request）。仓库的 README 把话说得很死：这只是研究代码，不是正式产品，公开出来的版本和文章里写的内部系统也不完全一样。

我把文章里的实验数据和这个仓库的代码放在一起翻了一遍。有几个地方光看文章很容易一带而过，但对照着代码看，挺有意思。

## 文章和原型的模块对照

文章用连续、高效、主动、持久四个词概括 Super-agent 的目标，下面拆了五个模块。因为在公开原型里部分命名和文章不太一样，有的模块干脆没放进来，先列一张对照表省得后面串线：

| 文章模块 | 处理的问题 | 公开原型里的实现 |
| --- | --- | --- |
| 双层架构（Router / Worker） | 既要持续响应，又要并发干活 | 一个主 Session（代码里叫 `orchestrator`），每个工单开一个执行器 Session（`worker`） |
| 事件驱动（Trigger / Thread / 订阅直通） | 主动触发与路由开销 | Source → Trigger → Thread → Eval → Ticket，靠 `Subscription` 把消息分发给工单 |
| 面向人的交互（全双工、多信道） | 别卡死对话，也别刷屏 | 前台 shell 命令跑满 5 秒自动转后台；聊天回复默认一句话，最多 100 词 |
| 计算、状态与环境分离 | 重启恢复与跨设备 | 跑在独立的本地 DSH Profile 里，靠本地状态目录和“先落盘、后执行”的队列扛住进程重启 |
| Watchdog | 异常自愈 | 公开原型的文档和代码里都没看到这一块 |

![每一层都只把需要上一层拍板的事情往上送：代码层准入过滤、攒批处理的 Router、靠订阅直通收消息的 Worker，以及最后只收到一条简短回复的人。](/blog/diagrams/super-agent-attention.svg)

## 一、给模型配了 Subagent 工具，它为什么不用？

第 7.1 节的消融实验里有一组挺扎眼的数据。

实验往系统里灌了大约 300 条群聊和 CI 消息，其中真正需要干活的请求大概 20 条，每组配置跑 5 轮。对照组是大家平时最熟悉的那种用法：单 Session 加一个 Subagent 工具，主会话觉得合适就把活派给子代理。

结果在中性提示词（“Use a subagent for a piece of work when appropriate...”）下，跑了 5 轮，模型调用 Subagent 的次数是 **0**。所有活全堆在主会话里自己干，中途不断被新涌进来的消息打断，p95 完成时间拖到了 29.5 分钟；而双层架构的 Super-agent 是 15.7 分钟。

后来团队把提示词改成明确要求“优先委派”，5 轮里总算有 4 轮派了子代理。但还是有 1 轮，模型觉得手头这件活很小，顺手就自己干了，结果那一次直接在耗时曲线上拉出一条长尾。

平时常写提示词的人大概都遇到过这种脾气。让模型派子代理，它得先组织语言把上下文写清楚，还得等那边跑完回报；而自己顺手跑个命令，在当下这一步看起来省事得多。单看每一次判断都很合理，但只要主会话亲自动手干一件“小活”，后面进来的消息就全堵在门口了。就像协作式多任务里一个死活不肯让出 CPU 的线程，每段代码看着都不长，整个系统却照样卡死。

指望靠提示词劝模型“顾全大局”显然不太靠谱。文章给出的办法很干脆：Router 层只管分发，不干具体活，甚至可以连 Bash 工具都不给。

翻看原型的代码，限制比文章写得还要死。主 Session 跑在单独的 `dsh-superagent-router` 预设下，能用的工具很少；宿主代码直接拦掉了 `sleep` 调用，shell 超时不允许超过 30 秒，等待后台任务不允许超过 5 秒。

执行器（`dsh-superagent-worker`）那边也做了类似的处理。文章里原本讲的是用异步 `start()` / `stop()` 做全双工 ReAct 循环（文章注明这个机制在 DeepSeek Harness 里已经写好了，只是还没默认打开）。公开原型没走这条路，而是用了一个更粗暴的规则：只要前台 shell 命令跑满 5 秒没结束，宿主就自动把它塞进后台任务，让执行器在下一步立刻腾出手来收新消息。命令到底该同步跑还是异步跑，根本不用模型自己拿主意。

## 二、7.2 节压测表里少算的一笔账

再看第 7.2 节的 Router 压力测试：

| Trigger 到达速率 | 平均 batch | 单次请求耗时 | 单个决定分摊耗时 |
| --- | --- | --- | --- |
| 约 1 条/分钟 | 1.0 | 2.5 秒 | 6.4 秒 |
| 约 40 条/分钟 | 2.8 | 3.9 秒 | 1.6 秒 |

消息涌入的速度涨了 40 倍，平均每个路由决定的耗时反而从 6.4 秒降到了 1.6 秒。文章给出的解释是：Router 每一步都是长输入、短输出，攒在一起的多个 Trigger 放进同一次请求里，正好在 GPU 的 Prefill 阶段并行算完，所以单次请求耗时只从 2.5 秒涨到 3.9 秒。

不过我顺手除了一下这几个数，发现光靠 Prefill 并行对不上账。

低负载下，单次请求 2.5 秒，做出一个决定要 6.4 秒，相当于每个决定平均要走 2.6 轮模型调用。到了高负载，单次请求 3.9 秒，如果一个决定还是得走 2.6 轮，那再怎么除以 2.8 的平均 batch，分摊下来也得 3.6 秒左右。但表里实测只有 1.6 秒——算下来每个决定只用了 0.4 轮调用，轮数足足少了 6 倍多。

省出来的轮数是哪来的？文章没细说，我去翻了原型里路由工具的定义。

原型里的 `orchestrator_route` 工具，参数直接就是一个数组，一次调用能同时塞进多条 `accept`、`attach`、`stop` 或 `ignore` 决定，每条独立校验生效，就算其中一条被打回也不耽误别的。同时，主 Session 的系统提示词明确要求：如果有多个候选事件在排队，那些光看事件卡片就能拍板的，直接打包进同一次 `orchestrator_route` 提交；只有实在拿不准、必须翻上下文的候选，才单独调读取工具，而且读取调用要和路由调用在同一轮里并发出去。

要是当初把路由工具设计成“一次调用只处理一条消息”，那哪怕 GPU Prefill 再快，每条消息也至少得占一轮工具往返。现在把工具签名设计成批量的，再配合“同一条 Thread 上同一时间只跑一个 Eval，期间新来的 Trigger 自动归入下一批”的串行队列，忙起来的时候连读上下文和交决定这两步都合着干了。这跟数据库里的组提交（group commit）或者网卡的中断合并是一个路数：平时来一条处理一条，真堵上了就顺势攒成一批走完。

## 三、订阅直通省下的不是时间

同一组消融实验里还有一行数据：把“订阅直通”（也就是某个工单订阅了一条 Thread 之后，后续该 Thread 上的新消息由代码直接塞给对应的 Worker，不再经过 Router）关掉。

关掉之后，任务的完成时间和完整版几乎没差别。变化的是另外两个数：Router 需要做的决定多了约 30%，缓存读取的 token 从 2323 万涨到了 3177 万，多了 37%。

刚看到这儿的时候我有点意外——既然上一节压测证明 Router 的吞吐量根本不是瓶颈，关掉直通也没拖慢任务速度，那费劲做这一层旁路干什么？

答案其实在上下文窗口的寿命上。整个系统里只有 Router 这一个主会话一直活着、拿着全局记忆。要是每个工单跟进过程中的讨论、CI 报错、补充说明全都从 Router 眼前过一遍，这些噪音就会一直垫在它的历史记录里。Token 账单涨了 37% 还是其次，更麻烦的是主会话的上下文窗口很快就会被无关细节塞满，压缩得越频繁，后面的路由判断就越容易犯糊涂。直通绕开 Router，图的就是别拿执行过程中的琐事去污染主会话的记忆。

## 四、能看见消息，不代表能发号施令

把 Agent 放进真实的 GitHub 仓库或群聊，最头疼的其实是杂音和越权。平时我们在群里聊工作，能看到消息的人就能插话提要求，聊着聊着话题沾边了大家就当成一件事处理。但如果让 Agent 也这么干，随便一条路人评论或者 CI 吐出来的日志都能把正在干活的 Worker 带偏。

原型在领域模型里把“收消息”“给权限”和“查背景”硬拆成了三件互不相干的事：

| 概念 | 在原型里干什么 | 明确禁止什么 |
| --- | --- | --- |
| Subscription（订阅） | 把 Thread 上的新消息（包括机器人和 CI 消息）转发给订阅了它的工单 | 不附带任何执行权限 |
| Mandate（授权） | 记录接单时的策略版本、权限范围、强度、命中的规则、发起人身份和来源渠道 | 不能扩权；超出原范围的事必须另开新工单 |
| Correlation（关联） | 评估时挂一点相关上下文供参考 | 绝不作为路由分发依据 |

这三者里，`Mandate` 卡得最死。只有接单那一刻能创建它；之后要么由人主动叫停，要么在策略文件更新后因为重新校验不过关而被系统吊销。除此之外，工单执行过程中收到的任何消息、评论或引用的文档，都只是普通的输入数据，改不动 `Mandate` 里的半个字。

翻看主 Session 的提示词，还有两条挺有意思的死规矩：

一条是“宁可重开，不可乱挂”。主 Session 只有在消息**明确点名**某个现有工单时，才允许把它 `attach` 上去——比如直接引用了那个工单的 PR、Issue、源消息或确认回复，或者聊的是刚刚改完的东西且全场只有一个工单对得上。光是“话题差不多”一律不准往上挂。提示词里解释得很实在：不小心重复开了一张工单，关掉就是了；可要是把不相干的消息挂错了工单，那个工单就会自动订阅整条 Thread，以后那条线上的所有动静都会源源不断地往里灌。

另一条是不准 Router 当“二传手”。主 Session 把请求转给执行器时，只准传原始 Trigger 的引用 ID 和必要的路由信息，严禁把别人的一句话需求扩写成工作计划，也不准自己往上添验收标准或检查清单。具体要干什么，执行器自己拿 ID 回原始消息里看。这跟文章 3.3 节讲的“链式召回”（用对象 ID 串起上下文，需要时再展开原文）是一个思路——Router 每替人总结一次，信息就走样一点，还不如直接传引用。

文章的第 8.4 节把安全与隐私归为“开放问题”，而公开原型专门用了一篇 `002-authorization.md` 来落地这套机制。里面还给主动规则加了个默认 `observe`（观察）模式：评估结果觉得“应该接单”时，先只记一笔日志、不真动手，等团队看过日志觉得靠谱了再切到 `auto`。

说到底，不管是防提示词注入，还是第一节里防模型大包大揽，原型的做法其实都一样：别指望模型光靠读一段文字警告就能管住自己。在原型的提示词优先级表里，排第一的是“工具和宿主代码强制执行的事实”，排在最末位的才是外部文本——文档里直接写着，外部文本只是数据，永远改不了规则和授权。

## 五、不再手动管 Session 之后，界面上还剩什么？

文章里提了一个挺准的判断：现在大家习惯手动建 Session、切 Session，很大程度上只是因为底层 LLM API 长这样，界面顺着 API 做了而已。

如果把 Session 藏到幕后，人平时盯着看的单位就变成了 `Ticket`（工单）。在原型的领域模型里，工单的状态是故意跟底层的 DSH Session 脱钩的——因为同一张工单中途可能会失败重试、进程重启后恢复，或者先后换好几个执行器接手（对应多个 `Assignment`）。对提需求的人来说这只是一件事，底下到底跑了几个会话并不重要。

要做到这一点，工单就得扛得住进程重启。原型里凡是拍板之后要做的动作——把候选事件转给主 Session、拉起 Assignment、投递输入、往外发回复——全都先写进本地状态目录，再异步执行，失败了就按退避策略重试。万一进程挂了重启，刚才跑了一半的 Assignment 会带着一段恢复提示重新拉起来，叮嘱执行器在重新执行任何外部操作之前，先去翻翻本地工作目录、`git log` 和 GitHub 上的状态。毕竟会话内存丢了也就丢了，之前评论发没发出去、PR 建没建好，去 GitHub 上看一眼就知道，没必要傻乎乎地再发一遍。

原型的状态面板也顺着这个思路做了减法。工单状态从上往下排，最顶上几栏全是以 `person / …` 开头的项：输入投递失败、等人类回话、等人类 Review PR、卡住或者彻底失败。正常在后台跑着的工单干脆不往眼前凑。文章第 8.2 节还在讨论脱离 Session 之后人机交互该长什么样，原型给出的方案其实就是个待办队列——按“哪件事正卡在人身上”来排优先级。

## 一层层往下挡噪音

把上面这些零碎的机制拼到一起，其实每一层都在干同一件事——替上一层挡掉不需要它操心的信息：

| 层级 | 最怕被什么拖垮 | 原型里的挡法 |
| --- | --- | --- |
| 人 | 群消息刷屏、不停被追问、自己记一堆会话的上下文 | 只有 Router 对外说话；聊天回复默认一句话、最多 100 词；接单确认只发一次；面板上只列卡在人身上的工单 |
| Router（主 Session） | 上下文被无关对话塞满，或者在某一步卡住导致全局排队 | 进模型前先过代码准入过滤；已订阅的 Thread 直接走旁路送给 Worker；路由备注限制在 30 词以内；平时不读代码也不查日志 |
| Worker（执行器 Session） | 一条长消息把上下文撑爆，或者被一条慢命令卡死 | Inline & Spill：事件卡片超过 600 字符就截断并留个续读指针；前台命令跑满 5 秒自动转后台 |

原型文档 `000-philosophy.md` 的第一条写得很白：“Take as little human attention as possible, and give as much value as possible.”

文章里虽然搬出了 Fast Path / Slow Path、批处理、缓存、投机执行、存算分离等一串系统工程概念，但落到代码里，核心都是在省“注意力”——不管是人的注意力，还是模型有限的上下文窗口。人盯不住那么多会话，就加一层 Router 替人看门；Router 的全局上下文金贵，就用订阅直通和 Worker 把具体干活的过程剥出去；Worker 自己的窗口也经不起长日志折腾，就靠 600 字符截断（Inline & Spill）和子代理再挡一层。

人脑同时能顾得上的事情还是只有 3 到 5 件，Super-agent 也没法让人长出三头六臂。它真正改变的是占住这 3 到 5 个坑位的东西：以前是你得自己记着前因后果的 3 到 5 个聊天窗口，现在变成 3 到 5 个已经跑出结果、只等你点个头或者批个 PR 的工单。

## 顺带聊聊插件生态与试用提醒

作为一个维护 DeepSeek Harness 插件目录的站点，我翻 `dsh-superagent-prototype` 时最先看的其实是它的目录结构。

它本身就是一个标准的 DeepSeek Harness bundle：根目录下一份 `cordis.patch.yml` 把插件挂进去，再给主 Session 和执行器各配一套预设，Harness 核心代码一行没动。之前我们在《[一切皆插件](/blog/notes/everything-is-a-plugin)》里聊过这套插件机制的边界，现在连官方团队探索 Super-agent 也是直接打成一个 Profile 扩展包来跑。

而且如果你读过前几天那篇《[DeepSeek Bot 生态全景](/blog/notes/deepseek-bot-ecosystem)》，看到这儿大概已经会心一笑了。社区项目 Tobs（`@botharness/tobs`）为了解决群聊收件箱卡死的问题，自己摸索出来的也是“常驻 Orchestrator 会话 + 后台 Assignment 会话”的双层结构，连命名都撞了一半。只要你真想让 Agent 在群聊里长期挂着干活，最后往往都会被逼到同一条架构路子上去。

最后提醒一句：如果你想在自己机器上跑一下这个原型，先看一眼它的权限配置。按仓库部署文档的说明，主 Session 和执行器两套预设默认都开了 `danger-full-access`，直接以当前系统用户的身份免审批跑命令；里面带的账号包装脚本只是切换默认凭据，并没有做进程级沙箱隔离。真要挂到群里或者仓库上跑，最好按文档建议单独建一个只放 Agent 凭据的受限系统用户，先把允许触发的名单收紧，主动规则留在默认的 `observe` 模式跑几天，看看日志里它打算接哪些单，心里有底了再切到 `auto`。
