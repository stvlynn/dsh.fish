먼저 작은 퀴즈 하나. 지금 당신은 에이전트 세션을 동시에 몇 개까지 따라갈 수 있나요?

DeepSeek Harness 팀이 10월 31일 공개한 글 「[Super-agent 设计探索：迈向更自主的 Agent 系统](https://telegra.ph/Super-agent-%E8%AE%BE%E8%AE%A1%E6%8E%A2%E7%B4%A2%E8%BF%88%E5%90%91%E6%9B%B4%E8%87%AA%E4%B8%BB%E7%9A%84-Agent-%E7%B3%BB%E7%BB%9F-10-31)」(Super-agent 설계 탐구: 더 자율적인 에이전트 시스템을 향하여)은 관찰값으로 3~5개를 제시합니다. 그 이상이 되면 사람은 어느 세션에서 무슨 말을 했는지 기억하지 못하게 됩니다. 글은 여기서 하나의 결론을 끌어냅니다. 단일 작업의 상한은 모델 능력이 정하고, 다중 작업의 상한은 사람의 주의력이 정한다는 것입니다.

이 문장은 한 번 더 곱씹어 볼 만합니다. 이런 시스템에서 가장 비싸고, 가장 느리고, 가장 늘릴 수 없는 부품이 GPU에서 화면 앞에 앉은 사람으로 옮겨 갔다는 뜻이니까요. 다음 질문을 머릿속에 두고 읽어 주세요.

> 기계에서 가장 희소한 부품이 사람이라면, 그 기계는 어떻게 설계해야 할까?

글과 함께 [`deepseek-ai/dsh-superagent-prototype`](https://github.com/deepseek-ai/dsh-superagent-prototype)도 공개되었습니다. DeepSeek Harness 번들 형태로 배포되는 연구 프로토타입으로, GitHub 저장소 하나와 (선택적으로) Feishu를 지켜보다가 허용된 요청을 티켓으로 만들고, 티켓마다 독립된 세션과 디렉터리에서 작업한 뒤 원래 대화로 돌아가 결과를 전달합니다. 결과물은 대개 Pull Request입니다. README 첫머리는 이것이 연구용 코드이고, DeepSeek가 정식 제품으로 내놓은 것이 아니며, 공개판은 글에서 설명한 내부 구현과 다르다고 분명히 밝힙니다.

원문의 구성은 이미 충분히 명료하니 절마다 다시 옮기지는 않겠습니다. 제가 하려는 일은 원문의 실험 수치와 프로토타입 코드를 나란히 놓고, 읽을 때는 그냥 넘어가기 쉽지만 생각할수록 이상해지는 지점 몇 곳을 짚어 보는 것입니다.

## 용어부터 맞춰 두기

원문은 Super-agent를 연속성, 효율, 능동성, 지속성이라는 네 가지 특징으로 정의하고, 다섯 개의 모듈로 그것을 떠받칩니다. 아래 표는 그 다섯 모듈과 공개 프로토타입 안의 대응물을 나란히 놓은 것입니다.

| 원문의 모듈 | 해결하는 문제 | 공개 프로토타입의 대응 |
| --- | --- | --- |
| 2계층 구조 (Router / Worker) | 연속성과 처리량의 트레이드오프 | 메인 세션 하나(코드에서는 `orchestrator`)와 티켓마다 하나씩인 실행 세션(`worker`) |
| 이벤트 구동 (Trigger / Thread / 구독 직통) | 능동성과 라우팅 비용 | Source → Trigger → Thread → Eval → Ticket, `Subscription`이 팬아웃 담당 |
| 사람을 향한 상호작용 (전이중, 다중 채널) | 막히지 않기, 도배하지 않기 | 5초를 넘긴 포그라운드 셸 명령은 자동으로 백그라운드로 이동. 채팅 답장은 기본 한 문장, 상한 100단어 |
| 연산·상태·환경의 분리 | 상시 가동과 기기 간 이동 | 공개 프로토타입은 로컬의 전용 DSH Profile에서 돌아가며, 로컬 상태 디렉터리와 '먼저 저장하고 나중에 실행하는' 작업 큐로 재시작을 버팀 |
| Watchdog | 이상 상황의 자가 복구 | 공개 프로토타입의 문서와 코드에서 대응 구현을 찾지 못함 |

## 1. 모델은 일을 맡기려 하지 않는다

원문 7.1절의 절제 실험(ablation)에 글 전체에서 가장 이상한 숫자가 숨어 있습니다.

실험은 약 300건의 채팅과 CI 메시지로 시스템을 구동하고, 그중 진짜 작업 요청은 약 20건입니다. 각 구성을 5번씩 돌립니다. 비교 대상은 '단일 세션 + Subagent 도구', 즉 오늘날 대부분의 사람이 에이전트를 쓰는 방식입니다. 메인 세션 하나가 있고, 적절하다 싶으면 서브에이전트에게 일을 넘깁니다.

중립적인 프롬프트("Use a subagent for a piece of work when appropriate...")에서 모델은 5번의 실행 동안 Subagent를 **단 한 번도** 호출하지 않았습니다. 모든 작업이 메인 세션에 몰렸고, 새 메시지가 올 때마다 끊겼으며, p95 완료 시간은 29.5분이었습니다. Super-agent의 p95는 15.7분이었습니다.

'위임을 우선하라'는 프롬프트로 바꾸자 5번 중 4번은 위임했습니다. 나머지 한 번은 모델이 이 일을 '작다'고 판단해 직접 처리했고, 그래프에 긴 꼬리를 남겼습니다.

잠깐 멈춰서 생각해 봅시다. 도구가 바로 손 닿는 곳에 있었는데, 모델은 왜 쓰지 않았을까요?

모델의 자리에서 보면 판단 하나하나는 다 말이 됩니다. 위임하려면 작업을 제대로 적어 주고 보고를 기다려야 합니다. 직접 하는 편이 빨라 보이고, 눈앞의 일은 실제로 작습니다. 한 걸음씩은 국소 최적이지만, 쌓이고 나면 전체 최악이 됩니다. 운영체제에서 CPU를 절대 스스로 내놓지 않는 스레드와 닮았습니다. 임계 구역 하나하나는 '짧은데' 기계 전체가 멈춰 버립니다.

원문의 처방은 소박합니다. Router 계층은 구체적인 작업을 실행하지 않으며, "Bash 도구조차 주지 않아도 된다"고 합니다. 프로토타입은 이것을 코드로 옮겼습니다. 메인 세션은 별도의 `dsh-superagent-router` 프리셋으로 돌아가며 도구가 더 적습니다. 호스트는 `sleep` 호출, 30초를 넘는 셸 타임아웃, 5초를 넘는 작업 대기를 거부합니다. 메인 세션이 한 단계에서 막히면 새로운 요청이 모두 그 뒤에 줄을 서야 하기 때문입니다.

실행 세션 쪽도 같은 생각입니다. 원문은 비동기 `start()` / `stop()`으로 전이중 ReAct 루프를 만들고, 이 메커니즘이 DeepSeek Harness에 이미 구현되어 있지만 기본으로 켜져 있지는 않다고 덧붙입니다. 프로토타입은 더 간편한 길을 택했습니다. `dsh-superagent-worker` 프리셋은 5초를 넘겨 실행되는 포그라운드 셸 명령을 자동으로 백그라운드 작업으로 옮기고, 실행 세션은 다음 단계에서 새 메시지를 받을 수 있습니다. 이 명령을 동기로 돌릴지 비동기로 돌릴지 모델이 판단할 필요조차 없습니다.

두 가지를 나란히 놓으면 규칙이 보입니다. **모델의 국소적 판단이 시스템 전체의 목표와 부딪치는 곳마다, 프로토타입은 그 선택지를 모델의 손에서 빼앗았습니다.** 프롬프트는 경향을 바꿀 수 있고, 보장을 줄 수 있는 것은 구조뿐입니다.

## 2. 정체가 처리량으로 바뀐다

두 번째로 자세히 볼 곳은 7.2절의 Router 부하 테스트입니다.

| Trigger 도착 속도 | 평균 배치 | 요청 1회 소요 시간 | 결정 1건당 분할 시간 |
| --- | --- | --- | --- |
| 분당 약 1건 | 1.0 | 2.5초 | 6.4초 |
| 분당 약 40건 | 2.8 | 3.9초 | 1.6초 |

도착 속도가 40배가 되었는데 결정 1건의 비용은 오히려 4분의 1이 되었습니다. 원문의 설명은 이렇습니다. Router의 각 단계는 입력이 길고 출력이 짧아서, 쌓인 Trigger를 한 번의 호출로 합치면 Prefill 단계에서 병렬로 계산되고, 요청 시간은 배치 크기보다 훨씬 느리게 늘어납니다.

여기에 작은 산수의 틈이 있습니다. 직접 계산해 보시길 권합니다.

저부하일 때 결정 1건에 6.4초, 요청 1회에 2.5초이니, 결정 하나에 모델 요청이 약 2.6회 필요합니다. 고부하일 때는 1.6 ÷ 3.9로 약 0.4회입니다. 횟수는 6배 넘게 줄었는데 배치는 2.8배밖에 커지지 않았습니다. 이득이 모두 '호출 한 번을 더 많은 Trigger로 나누는 것'에서 왔다면 분할 시간은 3.6초 근처에서 멈춰야 합니다. 실측은 1.6초입니다. 나머지는 어디서 왔을까요?

원문은 이 부분을 분해하지 않았습니다. 아래는 제가 프로토타입에서 찾은 단서입니다. 프로토타입의 라우팅 도구 `orchestrator_route`는 한 번의 호출에 accept, attach, stop, ignore 결정을 여러 개 담을 수 있고, 각 항목은 독립적으로 효력을 가지며, 한 항목이 거부되어도 나머지는 멈추지 않습니다. 메인 세션의 프롬프트도 여러 후보가 기다릴 때는 카드만으로 판단할 수 있는 것들을 한 번의 `orchestrator_route`로 묶어 보내고, 맥락을 정말 읽어야 하는 후보에게만 읽기 도구를 호출하되 그것도 라우팅 호출과 함께 보내라고 요구합니다.

즉, 배치 처리는 도구의 시그니처에도 새겨져 있습니다. 한 번에 결정 하나만 받는 도구는 모든 결정을 최소 한 번의 모델 왕복에 묶어 두고, Prefill이 아무리 빨라도 그 한 번은 없앨 수 없습니다. 부하가 올라가면 '맥락 읽기'와 '결정 제출'이라는 두 종류의 단계도 여러 Trigger가 함께 쓰게 되니, 결정 하나에 드는 횟수가 자연히 줄어듭니다.

시스템 공학에는 이런 동작의 선례가 많습니다. 네트워크 카드의 인터럽트 병합, 데이터베이스의 그룹 커밋. 부하가 낮으면 즉시 응답하고, 부하가 높으면 자동으로 합칩니다. 지연과 처리량을 각각 필요한 때에 얻는 장치입니다. 이들에게는 공통 전제가 있습니다. 순차 처리입니다. 프로토타입에서 한 Thread에서 동시에 도는 Eval은 최대 하나이고, 그사이 도착한 Trigger는 다음 배치에 합류합니다. 순차 처리는 보통 병목으로 여겨지지만, 여기서는 배치 처리의 원천입니다. 한 번에 한 배치만 처리하기 때문에 기다리는 이벤트들이 모일 기회가 생깁니다.

## 3. 직통이 아끼는 것은 맥락

세 번째 숫자는 같은 절제 실험에서 나왔고, 사소한 최적화로 읽고 지나치기 가장 쉽습니다.

구독 직통(같은 Thread의 후속 이벤트를 구독 중인 Worker에게 프로그램이 직접 보내는 장치)을 빼자, 작업 완료 시간은 완전판과 거의 같았습니다. 대신 Router가 내려야 할 결정은 약 30% 늘었고, 캐시 읽기 토큰은 2,323만에서 3,177만으로 37% 늘었습니다.

앞 절에서 Router의 처리량은 넉넉하다는 것이 드러났고, 직통이 작업을 빠르게 해 준 것도 아닙니다. 그렇다면 직통은 무엇을 지키고 있을까요?

답은 원문의 다른 한 문장에 있습니다. "컨텍스트 윈도를 낭비하는 것은 모델의 지능을 낭비하는 것이다." Router는 시스템에서 유일하게 전역 맥락을 쥔 세션이고, 본 이벤트는 모두 기억에 남아 이후 판단에 필요한 윈도를 잠식합니다. 직통은 Router와 무관한 이벤트를 Router가 보지 않아도 되게 해 줍니다. 아끼는 것은 Router의 주의력입니다.

여기까지 오면 처음의 질문이 조금 낯익게 느껴지기 시작할 겁니다.

## 4. 누가 듣고, 누가 정하고, 무엇이 관련되는가

평범한 단체 채팅에서는 세 가지가 한데 묶여 있습니다. 방에 있으면 모든 메시지가 보이고, 보이면 지시를 내릴 수 있으며, 주제가 비슷해 보이면 다들 같은 일이라고 여깁니다.

프로토타입은 이 셋을 서로 대신할 수 없는 세 개의 개념으로 나눴습니다.

| 관계 | 프로토타입의 개념 | 할 수 있는 일 | 일부러 할 수 없게 한 일 |
| --- | --- | --- | --- |
| 누가 듣는가 | Subscription(구독) | Thread의 모든 메시지를 그것을 구독하는 티켓에 팬아웃. 봇과 CI 메시지도 포함 | 어떤 권한도 부여하지 않음 |
| 누가 정하는가 | Mandate(위임) | 수락 시점의 정책 버전, 범위, 강도, 일치한 규칙, 요청자 신원, 수신 경로를 기록 | 범위 넓히기. 더 넓은 작업은 새 티켓이 필요 |
| 무엇이 관련되는가 | Correlation(연관) | 평가에 맥락을 보탬 | 라우팅에는 절대 관여하지 않음 |

Mandate의 규칙은 특히 엄격합니다. 수락이 그것을 만들고, 사람의 중지가 그것을 거둬들이며, 정책 변경 후 재검증에 실패하면 취소됩니다. 그 밖에 그것을 건드리는 길은 없습니다. 프로토타입 문서는 단도직입적입니다. 메시지, 댓글, 인용된 문서는 모두 결정의 입력일 뿐이며 권한을 바꿀 수 없다고 말합니다.

이 분리가 얼마나 진지한지 보여 주는 세부가 두 가지 있습니다.

첫째, 메인 세션은 메시지가 어떤 티켓을 **명시적으로 가리킬 때만** 그 메시지를 해당 티켓에 붙일 수 있습니다. 티켓의 PR이나 Issue, 원본 메시지, 접수 답장을 인용하거나 링크했을 때, 또는 방금 끝난 변경을 언급하는데 맞는 티켓이 정확히 하나일 때입니다. 주제가 비슷한 것은 쳐 주지 않습니다. 이유는 프롬프트에 적혀 있습니다. 중복으로 열린 티켓은 닫으면 되지만, 잘못 붙인 메시지는 티켓이 Thread 전체를 구독하게 만들고 그대로 남습니다. 두 가지 오류의 비용이 비대칭이니, 규칙은 비용이 싼 쪽으로 기울어 있습니다.

둘째, 메인 세션은 요청을 전달할 때 원래 Trigger에 대한 참조와 라우팅 사실만 가져갑니다. 짧은 요청을 작업 계획으로 고쳐 쓰는 것도, 인수 기준을 덧붙이는 것도, 체크리스트를 다는 것도 금지되어 있고, 요구 사항은 실행 세션이 원래 출처로 돌아가 스스로 도출합니다. Router가 한 번 고쳐 쓸 때마다 손실 압축이 한 번 일어나고, 말 전하기 게임은 세 번째 사람에게서 이미 뜻이 비틀립니다. 참조를 넘기면 Worker는 언제나 1차 자료를 읽습니다. 원문 3.3절의 '연쇄 회상(chain of recall)'이 ID로 객체 그래프를 엮는 것과 같은 수법입니다.

원문은 보안과 프라이버시를 8.4절의 열린 문제로 꼽습니다. 공개 프로토타입은 도메인 모델 바로 다음, 실행 앞에 번호가 매겨진 문서 한 편(`002-authorization.md`)을 통째로 권한에 할애합니다. 그 안에는 원문 3.4절의 투기적 실행과 꼭 닮은 설계도 있습니다. 능동 규칙은 기본적으로 `observe` 모드에서 돌며, 평가 결론이 '수락하겠다'여도 기록만 하고 행동하지 않습니다. 팀이 그 기록을 검토한 다음에야 `auto`로 전환합니다. 원문이 투기적으로 실행하는 대상은 작업이고, 프로토타입이 투기적으로 실행하는 대상은 권한입니다.

1절과 이 절을 나란히 놓으면 더 깊은 대칭이 보입니다. 위임하지 않는 모델은 자기 사전 지식에 설득된 것이고, 프롬프트 인젝션은 외부 텍스트에 설득된 것입니다. 두 실패는 모양이 똑같습니다. 주의력을 가진 모델에게 텍스트를 읽어서 스스로를 단속하라고 맡긴 것입니다. 프로토타입이 둘에게 내리는 처방도 같습니다. 결정을 컨텍스트 윈도 밖으로 옮겨 호스트 코드에 맡기는 것. 프롬프트 우선순위 표의 맨 위에는 '도구와 호스트가 강제하는 사실'이 있고, 맨 아래에는 외부 텍스트가 있으며, 문서는 그것을 "데이터이며 규칙이나 권한을 결코 바꾸지 못한다"고 적습니다.

## 5. 세션이 무대 뒤로 물러난 뒤 무대에 남는 것

원문에는 사용자에게 세션을 직접 관리하게 하는 것은 상당 부분 하위 LLM API에서 이어져 온 설계 관성이라는 판단이 있습니다. 그렇다면 세션이 퇴장한 뒤 사용자가 마주하는 단위는 무엇일까요?

프로토타입의 답은 Ticket(티켓), 즉 권한을 부여받은 작업 한 단위입니다. 도메인 모델은 티켓의 상태를 DSH 세션의 상태와 일부러 분리합니다. 하나의 티켓은 재시도되고, 재시작 후 복구되며, 여러 실행 세션이 차례로 이어받기도 해서, 생애 동안 여러 Assignment에 걸치기 때문입니다. 사용자가 보는 것은 하나의 약속이고, 기계가 돌리는 것은 일련의 세션입니다.

약속은 재시작을 넘어가야 합니다. 프로토타입에서 결정 이후에 하는 일(메인 세션으로 후보 전달, Assignment 시작, 입력 전달, 답장 발송)은 모두 먼저 저장하고 나중에 실행하며, 실패하면 백오프와 함께 재시도합니다. 프로세스가 재시작되면 중단된 Assignment는 복구 메모를 달고 다시 시작하고, 외부 동작을 반복하기 전에 자기 디렉터리, git 이력, GitHub를 먼저 확인하라고 실행 세션에 요구합니다.

이 메모 뒤에는 소박한 관찰이 있습니다. 에이전트의 기억은 사라질 수 있지만, 바깥 세계에 남긴 흔적은 그대로 있습니다. 댓글을 올렸는지, PR을 열었는지는 GitHub를 보면 압니다. 재시작 뒤에 먼저 세계를 읽고 나서 움직일지 정하면, 바깥 세계가 가장 믿을 만한 로그가 됩니다.

패널에 대한 프로토타입의 원칙은 사람이 필요한 것만 보여 주는 것입니다. 티켓 단계는 위에서부터 차례로 맞춰 보며, 맨 앞의 몇 줄은 모두 `person / …`입니다. 입력 전달 실패, 답변 대기, 검토 대기, 막힘 또는 실패. 건강한 상태는 자리를 차지하지 않습니다.

원문 8.2절은 세션을 벗어난 뒤 사람이 에이전트와 어떻게 협업해야 하는지 묻습니다. 프로토타입이 내놓은 구체적인 답 하나는 인터페이스를 '사람이 무엇을 해야 하는가' 순으로 정렬한 큐로 만드는 것이었습니다.

## 처음의 질문으로 돌아가기

흩어진 단서를 이제 모아 봅시다. 시스템에서 주의력을 쥔 주체를 계층별로 늘어놓고, 원문과 프로토타입이 각각 무엇을 막아 주는지 보겠습니다.

| 주의력의 주체 | 두려워하는 것 | 막아 주는 장치 |
| --- | --- | --- |
| 사람 | 메시지 폭탄, 끝없는 질문, 세션 세부를 기억해야 하는 부담 | Router가 대외 창구를 일원화. 채팅 답장은 기본 한 문장, 상한 100단어. 접수 확인은 한 번만. 패널은 건강한 상태를 숨김 |
| Router(메인 세션) | 무관한 이벤트로 맥락이 차는 것, 실행 세부에 발목 잡히는 것 | 모델 앞의 결정적 게이트. 구독 직통으로 Router를 우회. 라우팅 메모는 30단어 이내. 능동 평가 외에는 코드도 로그도 읽지 않음 |
| Worker(실행 세션) | 긴 텍스트로 맥락이 넘치는 것, 긴 명령에 막히는 것 | Inline & Spill: 이벤트 카드는 600자로 자르고 이어 읽기 포인터를 붙임. 포그라운드 명령은 5초 뒤 백그라운드로 |

세 줄이 하는 말은 같습니다. **주의력이 가장 비싼 주체에게 가장 적게 보여 주고, 그것도 그 주체의 결정이 필요한 부분만 보여 준다.** 프로토타입의 `000-philosophy.md`는 이를 프로젝트 전체의 제1원칙으로 적어 둡니다. "Take as little human attention as possible, and give as much value as possible."

원문은 다섯 개의 모듈을 쓰고, 컴퓨터 시스템의 오래된 개념을 줄줄이 빌려 옵니다. Fast Path와 Slow Path, 배치 처리, 캐시, 투기적 실행, 연산과 저장의 분리, 워치독. 끝까지 읽고 나면 이 모듈들이 하나의 원칙을 서로 다른 계층에서 펼친 것임을 알게 됩니다. 사람이 자기 주의력을 지키려다 Router가 생겼고, Router가 자기 주의력을 지키려다 직통과 Worker가 생겼고, Worker가 자기 주의력을 지키려다 Inline & Spill과 Subagent가 생겼습니다. 아키텍처 전체가 재귀적이며, 각 계층은 한 층 위의 주의력을 예산으로 삼습니다.

이것으로 1절과 4절의 대칭도 설명됩니다. 이런 시스템에서 가장 위험한 설계는 주의력을 가진 주체에게 주의력을 아낄지, 눈앞의 텍스트를 믿을지를 스스로 정하게 하는 것입니다. 그 주체의 손에는 텍스트밖에 없으니까요. 답은 구조 안에 둘 수밖에 없습니다.

그러니 처음의 3~5로 돌아가 봅시다. Super-agent는 이 숫자를 움직이지 못합니다. 사람이 동시에 따라갈 수 있는 양은 그대로입니다. 움직일 수 있는 것은 그 칸에 들어가는 내용입니다. 맥락을 기억해야 하는 세션 3~5개가, 당신의 결재만 기다리는 결정 3~5개로 바뀝니다.

## 플러그인 생태계에 주는 의미

마지막으로 이 사이트의 관심사로 돌아옵니다.

`dsh-superagent` 자체가 DeepSeek Harness 번들입니다. `cordis.patch.yml` 하나가 플러그인을 끼워 넣고, 메인 세션과 실행 세션용 프리셋을 하나씩 정의하며, Harness 코어는 한 줄도 건드리지 않습니다. 「[모든 것은 플러그인이다](/blog/notes/everything-is-a-plugin)」에서 다룬 아키텍처 원칙이 또 한 번 확인된 셈입니다. Super-agent 같은 형태조차 플러그인으로 Profile에 들어갑니다.

또 하나의 우연은 더 흥미롭습니다. [DeepSeek Bot 생태계 글](/blog/notes/deepseek-bot-ecosystem)에서 소개한 커뮤니티 프로젝트 Tobs는 상주하는 Orchestrator 세션과 백그라운드 Assignment 세션이라는 2계층 구조에 독자적으로 도달했습니다. 원문은 "비슷한 설계 제약은 비슷한 아키텍처 선택으로 이어진다"고 말하는데, 이 카탈로그에 마침 그 실례가 있는 셈입니다.

프로토타입을 써 볼 생각이라면 그 위치를 잊지 마세요. 배포 가이드에 따르면 두 프리셋 모두 `danger-full-access`로 운영자의 OS 사용자 권한으로 실행되고, 실행 세션은 승인 없이 명령을 실행합니다. 계정 래퍼는 기본으로 어떤 자격 증명을 쓸지만 고를 뿐 프로세스를 격리하지는 못합니다. 격리가 필요하면 에이전트 자격 증명만 둔 전용 OS 계정을 마련하라고 가이드는 권합니다. 시작 순서도 프로토타입의 권고를 따르세요. 허용 목록은 짧게 두고, 능동 규칙은 `observe` 모드에 둔 채 '원래라면 무엇을 했을지' 확인한 다음 조금씩 넓혀 가면 됩니다.
