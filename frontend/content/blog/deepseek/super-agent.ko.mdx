평소 컴퓨터에서 에이전트 세션을 동시에 서너 개나 대여섯 개쯤 띄워 놓으면 그게 제 한계입니다. 창을 더 열면 어느 세션에 무슨 지시를 내렸는지 금방 헷갈리기 시작하고, 결국 모든 창이 제 답장만 기다리며 멈춰 서게 됩니다.

10월 31일 DeepSeek Harness 팀이 공개한 「[Super-agent 设计探索：迈向更自主的 Agent 系统](https://telegra.ph/Super-agent-%E8%AE%BE%E8%AE%A1%E6%8E%A2%E7%B4%A2%E8%BF%88%E5%90%91%E6%9B%B4%E8%87%AA%E4%B8%BB%E7%9A%84-Agent-%E7%B3%BB%E7%BB%9F-10-31)」(Super-agent 설계 탐구: 더 자율적인 에이전트 시스템을 향하여)에서도 관찰값으로 똑같이 3~5개를 꼽았습니다. 글의 요지는 단순합니다. 단일 작업의 상한은 모델 능력이 정하지만, 다중 작업의 상한은 사람의 주의력이 정한다는 것입니다. 지금 시스템 전체를 붙잡아 두는 병목은 대개 GPU가 아니라, 화면 앞에 앉은 사람이 머릿속에 동시에 담아 둘 수 있는 맥락의 개수입니다.

이 글과 함께 [`deepseek-ai/dsh-superagent-prototype`](https://github.com/deepseek-ai/dsh-superagent-prototype)도 공개되었습니다. DeepSeek Harness 번들로 묶인 연구 프로토타입인데, GitHub 저장소나 Feishu 채팅방을 지켜보다가 허용된 요청이 올라오면 티켓으로 바꾸고, 각자 독립된 세션과 디렉터리에서 작업을 마친 뒤 원래 대화방으로 돌아와 결과(보통은 Pull Request)를 전달합니다. 저장소 README는 시작부터 선을 분명히 긋습니다. 연구용 코드일 뿐 정식 제품이 아니며, 공개된 버전은 글에서 설명하는 사내 시스템과 완전히 같지도 않습니다.

글에 나온 실험 데이터와 저장소 코드를 나란히 펼쳐 놓고 읽어 보았습니다. 본문만 읽을 때는 그냥 지나치기 쉽지만, 실제 코드와 맞춰 보면 꽤 흥미로운 구석이 여럿 있습니다.

## 글과 프로토타입의 모듈 대조

글은 Super-agent의 목표를 연속, 고효율, 능동, 지속이라는 네 단어로 요약하고 그 아래 다섯 개의 모듈을 둡니다. 공개 프로토타입에서는 일부 용어가 다르거나 아예 빠진 모듈도 있어서 먼저 표로 맞춰 두는 편이 헷갈리지 않습니다.

| 글의 모듈 | 다루는 문제 | 공개 프로토타입의 구현 |
| --- | --- | --- |
| 2계층 구조 (Router / Worker) | 응답을 멈추지 않으면서 동시에 여러 작업 돌리기 | 메인 세션 하나(코드에서는 `orchestrator`)와 티켓마다 열리는 실행 세션(`worker`) |
| 이벤트 구동 (Trigger / Thread / 구독 직통) | 능동적 트리거와 라우팅 비용 | Source → Trigger → Thread → Eval → Ticket, `Subscription`으로 티켓에 메시지 배포 |
| 사람을 향한 상호작용 (전이중, 다중 채널) | 대화가 막히거나 알림으로 도배되지 않게 하기 | 5초를 넘긴 포그라운드 셸 명령은 자동으로 백그라운드로 전환. 채팅 답장은 기본 한 문장, 최대 100단어 |
| 연산·상태·환경 분리 | 프로세스 재시작 복구와 기기 간 이동 | 독립된 로컬 DSH Profile에서 돌며, 로컬 상태 디렉터리와 '선 저장 후 실행' 큐로 프로세스 재시작을 버팀 |
| Watchdog | 이상 발생 시 자가 복구 | 공개 프로토타입의 문서와 코드에는 빠져 있음 |

![각 계층은 위 계층이 결정해야 할 일만 위로 올린다. 코드 단계의 통과 필터, 배치를 모으는 Router, 구독 직통으로 메시지를 받는 Worker, 그리고 짧은 답장 하나만 받는 사람.](/blog/diagrams/super-agent-attention.svg)

## 1. 모델에게 Subagent 도구를 줬는데, 왜 쓰지 않을까?

7.1절의 절제 실험(ablation)에 꽤 눈에 띄는 수치가 있습니다.

실험은 약 300건의 단체 채팅 및 CI 메시지를 시스템에 흘려보내고(그중 실제 작업 요청은 약 20건), 각 구성을 5번씩 돌렸습니다. 대조군은 우리가 평소 가장 흔히 쓰는 방식인 '단일 세션 + Subagent 도구'입니다. 메인 세션이 상황을 봐서 서브에이전트에게 일을 넘기는 구성이죠.

그런데 중립적인 프롬프트("Use a subagent for a piece of work when appropriate...")로 5번을 돌린 결과, 모델이 Subagent를 호출한 횟수는 **0번**이었습니다. 모든 작업을 메인 세션 안에서 혼자 처리하려다 새로 밀려드는 메시지에 계속 끊겼고, p95 완료 시간은 29.5분까지 늘어졌습니다. 2계층 구조인 Super-agent는 15.7분이었습니다.

프롬프트를 '위임을 우선하라'고 직접 지시하는 문구로 바꾸자 5번 중 4번은 서브에이전트를 불렀습니다. 하지만 남은 1번에서는 모델이 눈앞의 일을 '작다'고 판단해 직접 손을 댔고, 그 한 번이 지연 시간 그래프에 긴 꼬리를 만들어 냈습니다.

에이전트 프롬프트를 만져 본 사람이라면 이 고집이 낯설지 않을 겁니다. 서브에이전트에게 일을 맡기려면 맥락을 정리해 지시문을 적고 결과 보고를 기다려야 하지만, 당장 내가 명령 한 줄 치는 건 그 순간만 보면 훨씬 간편해 보입니다. 매 단계의 판단만 놓고 보면 합리적이지만, 메인 세션이 '작은 일' 하나를 직접 처리하기 시작하는 순간 뒤이어 들어오는 메시지는 전부 문 앞에서 줄을 서야 합니다. 협력적 멀티태스킹에서 금방 끝난다며 CPU를 내놓지 않는 스레드 하나 때문에 시스템 전체가 얼어붙는 것과 똑같습니다.

프롬프트로 모델에게 '전체적인 흐름을 배려하라'고 설득하는 건 믿을 만한 방법이 못 됩니다. 글이 내놓은 해법은 아주 단호합니다. Router 계층은 구체적인 작업을 아예 실행하지 않으며, 심지어 Bash 도구를 주지 않아도 된다는 것입니다.

프로토타입 코드를 열어 보면 제약이 글보다 더 빡빡합니다. 메인 세션은 별도의 `dsh-superagent-router` 프리셋으로 돌며 쓸 수 있는 도구가 몇 개 없습니다. 호스트 코드가 아예 `sleep` 호출을 막아 버리고, 30초를 넘는 셸 타임아웃이나 5초를 넘는 백그라운드 작업 대기도 거부합니다.

실행기(`dsh-superagent-worker`) 쪽도 비슷한 방식을 씁니다. 글에서는 비동기 `start()` / `stop()`으로 전이중 ReAct 루프를 구성한다고 설명하지만(DeepSeek Harness에 이미 구현되어 있으나 기본값은 꺼져 있다고 덧붙입니다), 공개 프로토타입은 훨씬 단순한 규칙을 택했습니다. 포그라운드 셸 명령이 5초 안에 끝나지 않으면 호스트가 자동으로 백그라운드 작업으로 넘겨 버려서, 실행기가 바로 다음 단계에 새 메시지를 받을 수 있게 만듭니다. 이 명령을 동기로 돌릴지 비동기로 돌릴지 모델이 고민할 여지조차 주지 않습니다.

## 2. 7.2절 부하 테스트 표에서 빠진 계산 한 가지

다음으로 7.2절의 Router 부하 테스트를 보겠습니다.

| Trigger 도착 속도 | 평균 배치 | 요청 1회 소요 시간 | 결정 1건당 분할 시간 |
| --- | --- | --- | --- |
| 분당 약 1건 | 1.0 | 2.5초 | 6.4초 |
| 분당 약 40건 | 2.8 | 3.9초 | 1.6초 |

메시지 유입 속도가 40배로 뛰었는데 라우팅 결정 한 건당 걸리는 시간은 오히려 6.4초에서 1.6초로 줄었습니다. 글의 설명은 이렇습니다. Router의 매 단계는 입력이 길고 출력이 짧아서, 밀려 있는 여러 Trigger를 한 번의 요청에 묶어 넣으면 GPU의 Prefill 단계에서 병렬로 계산되므로 요청 1회 소요 시간이 2.5초에서 3.9초로밖에 늘지 않는다는 것입니다.

그런데 이 숫자들을 직접 나눠 보니 Prefill 병렬화만으로는 계산이 맞지 않았습니다.

저부하일 때 요청 한 번이 2.5초이고 결정 하나에 6.4초가 걸린다는 건, 결정 하나를 내리는 데 평균 2.6회의 모델 호출이 필요하다는 뜻입니다. 고부하일 때는 요청 한 번이 3.9초입니다. 만약 고부하에서도 결정 하나에 여전히 2.6회의 호출이 필요하다면, 평균 배치 크기인 2.8로 나눠도 3.6초 근처가 나와야 합니다. 하지만 표에 적힌 실측값은 1.6초입니다. 역산해 보면 결정 하나당 약 0.4회의 호출만 썼다는 뜻이고, 왕복 횟수 자체가 6분의 1 이하로 줄어든 셈입니다.

줄어든 왕복 횟수는 어디서 나왔을까요? 글에는 자세한 설명이 없어서 프로토타입의 라우팅 도구 정의를 찾아보았습니다.

프로토타입의 `orchestrator_route` 도구는 인자가 애초에 배열로 되어 있어서, 한 번 호출할 때 여러 개의 `accept`, `attach`, `stop`, `ignore` 결정을 한꺼번에 넣을 수 있습니다. 각 항목은 독립적으로 검증·적용되므로 하나가 거절되어도 나머지는 그대로 처리됩니다. 게다가 메인 세션의 시스템 프롬프트는 후보 여러 개가 대기 중일 때 이벤트 카드만 보고도 판단이 서는 것들은 한 번의 `orchestrator_route` 호출로 묶어서 제출하고, 정말 맥락을 더 읽어야 하는 후보에 대해서만 읽기 도구를(그것도 라우팅 호출과 동시에) 부르도록 지시합니다.

만약 라우팅 도구가 '호출 한 번에 메시지 하나만 처리'하도록 설계되어 있었다면, GPU Prefill이 아무리 빨라도 메시지마다 최소 한 번의 도구 왕복이 붙었을 겁니다. 도구 시그니처 자체를 배치 형태로 만들고, 여기에 "같은 Thread에서는 동시에 하나의 Eval만 돌며 그사이에 도착한 Trigger는 다음 배치로 합친다"는 순차 큐 규칙을 얹은 덕분에, 바쁠 때는 맥락 읽기와 결정 제출 단계까지 여러 이벤트가 함께 처리됩니다. 데이터베이스의 그룹 커밋(group commit)이나 네트워크 카드의 인터럽트 병합과 같은 원리입니다. 한가할 때는 하나씩 바로 처리하고, 밀리기 시작하면 자연스럽게 배치로 묶어 넘깁니다.

## 3. 구독 직통이 아끼는 것은 시간이 아니다

같은 절제 실험 표에는 '구독 직통'(티켓이 특정 Thread를 구독한 뒤, 그 Thread에 올라오는 후속 메시지를 Router를 거치지 않고 코드가 곧바로 해당 Worker에 넣어 주는 우회로)을 껐을 때의 수치도 나와 있습니다.

직통을 꺼도 작업 완료 시간은 전체 기능 버전과 거의 차이가 없었습니다. 대신 달라진 숫자가 두 개 있는데, Router가 내려야 하는 결정이 약 30% 늘었고 캐시 읽기 토큰이 2,323만에서 3,177만으로 37% 뛰었습니다.

처음 이 대목을 봤을 때는 조금 의아했습니다. 앞 절의 부하 테스트에서 Router의 처리량이 충분하다는 걸 이미 보여 줬고, 직통을 꺼도 작업 속도가 느려지지 않는데 왜 굳이 우회로를 만들었을까요?

답은 컨텍스트 윈도의 수명에 있습니다. 시스템 전체에서 처음부터 끝까지 살아남아 전역 기억을 쥐고 있는 세션은 Router 하나뿐입니다. 만약 각 티켓을 처리하는 과정에서 오가는 토론, CI 오류 로그, 추가 설명이 전부 Router 눈앞을 지나가야 한다면 그 잡음이 고스란히 대화 이력에 쌓입니다. 토큰 비용이 37% 더 나오는 건 둘째 문제고, 메인 세션의 컨텍스트 윈도가 금방 자잘한 내역으로 가득 차서 압축이 잦아지고 뒤이은 라우팅 판단이 흐려지는 것이 진짜 문제입니다. 직통으로 Router를 우회하는 건 실행 과정의 잡다한 대화로 메인 세션의 기억을 더럽히지 않으려는 것입니다.

## 4. 메시지를 볼 수 있다고 지시를 내릴 수 있는 건 아니다

에이전트를 실제 GitHub 저장소나 시끌벅적한 단체 채팅방에 붙여 보면 가장 골치 아픈 것이 잡음과 월권입니다. 사람끼리 일하는 채팅방에서는 방에 있는 누구나 끼어들어 요구 사항을 말할 수 있고, 주제가 비슷해 보이면 알아서 같은 일로 묶어 처리합니다. 하지만 에이전트에게 똑같이 맡겨 두면 지나가던 댓글 하나나 CI가 뱉어 낸 로그 때문에 작업 중이던 Worker가 엉뚱한 길로 새기 십상입니다.

프로토타입은 도메인 모델에서 '메시지 수신', '권한 부여', '배경 참고'를 서로 섞이지 않는 세 가지 개념으로 쪼개 놓았습니다.

| 개념 | 프로토타입에서 하는 일 | 명시적으로 금지하는 것 |
| --- | --- | --- |
| Subscription (구독) | Thread에 올라오는 새 메시지(봇 및 CI 메시지 포함)를 구독 중인 티켓에 전달 | 실행 권한은 일절 부여하지 않음 |
| Mandate (위임) | 수락 시점의 정책 버전, 권한 범위, 강도, 일치한 규칙, 요청자 신원, 유입 경로를 기록 | 권한 범위 확대 불가. 범위를 벗어난 일은 새 티켓을 열어야 함 |
| Correlation (연관) | 평가할 때 참고용 관련 맥락을 덧붙임 | 라우팅이나 배정 근거로는 절대 쓰지 않음 |

이 셋 중에서 `Mandate`가 가장 엄격하게 묶여 있습니다. 오직 티켓을 수락하는 그 순간에만 만들어지며, 이후에는 사람이 직접 중지를 명령해 거둬들이거나 정책 파일이 바뀐 뒤 재검증을 통과하지 못해 취소되는 길밖에 없습니다. 티켓이 돌아가는 동안 들어오는 어떤 메시지나 댓글, 참조 문서도 모두 단순한 입력 데이터일 뿐이며 `Mandate`의 내용은 한 글자도 바꾸지 못합니다.

메인 세션의 프롬프트를 읽어 보면 꽤 단호한 규칙 두 가지가 더 나옵니다.

첫째는 "애매하면 기존 티켓에 붙이지 말고 새로 열라"는 것입니다. 메인 세션이 메시지를 기존 티켓에 `attach`할 수 있는 경우는 그 메시지가 해당 티켓의 PR이나 Issue, 원본 메시지, 접수 확인 답장을 **직접 인용·링크**했거나, 방금 끝난 변경 사항을 말하는데 들어맞는 티켓이 딱 하나뿐일 때로 한정됩니다. 단순히 '주제가 비슷해 보인다'는 이유로는 붙이지 못합니다. 프롬프트에 적힌 이유가 현실적입니다. 실수로 중복 티켓을 열었다면 닫으면 그만이지만, 상관없는 메시지를 잘못 `attach`하면 그 티켓이 Thread 전체를 구독하게 되어 이후 그 줄기에 올라오는 모든 잡음이 끝없이 흘러들어 오기 때문입니다.

둘째는 Router가 중간에서 말을 옮기며 살을 붙이지 못하게 막은 것입니다. 메인 세션이 실행기에게 요청을 넘길 때는 원본 Trigger의 참조 ID와 필수 라우팅 정보만 전달합니다. 짧은 한 줄짜리 요청을 작업 계획서로 부풀려 쓰거나, 자체적으로 인수 기준이나 체크리스트를 덧붙이는 행위는 금지되어 있으며, 실행기가 직접 참조 ID를 들고 원본 메시지로 돌아가 요구 사항을 파악합니다. 글 3.3절의 '연쇄 회상(chain of recall, 객체들을 ID로 엮어 두고 필요할 때 원문을 펼쳐 보는 방식)'과 같은 발상인데, Router가 중간에서 요약할 때마다 정보가 조금씩 왜곡되는 일을 아예 차단한 것입니다.

글의 8.4절은 보안과 프라이버시를 '열린 문제'로 남겨 두었지만, 공개 프로토타입은 실행 단계에 들어가기 전에 `002-authorization.md` 문서 한 편을 통째로 할애해 이 권한 체계를 박아 두었습니다. 또한 능동 규칙에는 기본값으로 `observe`(관찰) 모드를 두어서, 평가 결과가 '수락해야 함'으로 나와도 일단 로그에만 적고 실제 작업은 벌이지 않게 했습니다. 팀이 로그를 확인해 보고 믿을 만하다고 판단했을 때 `auto`로 바꾸면 됩니다.

결국 프롬프트 인젝션을 막는 방식이나 1절에서 모델이 일을 혼자 떠안지 못하게 막는 방식이나 뿌리는 같습니다. 모델에게 경고문을 읽혀서 스스로 자제하기를 기대하지 않는다는 것입니다. 프로토타입의 프롬프트 우선순위 표에서 맨 꼭대기는 '도구와 호스트 코드가 강제하는 사실'이고, 외부 텍스트는 '규칙이나 권한을 절대 바꿀 수 없는 데이터'로서 맨 아래에 놓여 있습니다.

## 5. 세션을 수동으로 관리하지 않게 되면 화면에는 무엇이 남을까?

글에서 꽤 공감이 갔던 지적 중 하나는, 사용자에게 세션을 직접 만들고 전환하게 하는 지금의 방식이 실은 하위 LLM API의 모양을 그대로 화면에 옮겨 놓은 관성에 가깝다는 점이었습니다.

세션을 무대 뒤로 숨기고 나면 사람이 평소 마주하는 단위는 `Ticket`(티켓)이 됩니다. 프로토타입의 도메인 모델은 티켓의 상태를 DSH 세션과 일부러 분리해 두었습니다. 티켓 하나가 도중에 실패해 재시도되거나, 프로세스가 재시작된 뒤 복구되거나, 여러 실행기(`Assignment`)를 거치며 이어달리기를 할 수 있기 때문입니다. 일을 시킨 사람 입장에서는 여전히 하나의 작업일 뿐이고, 그 아래에서 세션이 몇 개나 돌았는지는 신경 쓸 필요가 없습니다.

그러려면 티켓이 프로세스 재시작을 견뎌 내야 합니다. 프로토타입에서는 결정 이후에 일어나는 모든 후속 동작—메인 세션으로 후보 전달, Assignment 시작, 입력 전달, 답장 발송—을 로컬 상태 디렉터리에 먼저 기록한 뒤 비동기로 실행하고, 실패하면 백오프 전략에 따라 재시도합니다. 만약 프로세스가 죽었다가 다시 살아나면 중단되었던 Assignment는 복구 안내문을 달고 다시 시작하는데, 외부 동작을 다시 수행하기 전에 반드시 로컬 작업 디렉터리와 `git log`, GitHub 상태를 먼저 확인하라고 실행기에게 일러둡니다. 세션 메모리는 날아갔더라도 댓글을 이미 달았는지, PR을 이미 열었는지는 GitHub에 다 남아 있으니 똑같은 댓글이나 PR을 두 번 올리는 참사를 막을 수 있습니다.

상태 패널도 같은 기준으로 덜어 냈습니다. 티켓 상태를 위에서부터 차례로 대조하는데, 맨 위에 놓인 항목들은 전부 `person / …`으로 시작합니다. 입력 전달 실패, 사람의 답변 대기, PR 리뷰 대기, 막힘 혹은 실패 상태입니다. 백그라운드에서 정상적으로 돌고 있는 티켓은 아예 눈앞에 띄우지 않습니다. 글 8.2절은 세션에서 벗어난 뒤 사람과 에이전트가 어떻게 협업해야 하는지 묻고 있는데, 프로토타입이 내놓은 답은 화면을 '지금 사람 때문에 멈춰 있는 일' 순서로 정렬된 대기열로 만드는 것이었습니다.

## 계층마다 아래로 내려가며 잡음 걸러 내기

지금까지 살펴본 장치들을 모아 놓고 보면, 결국 모든 계층이 자기 바로 위 계층을 대신해 불필요한 정보를 막아 주는 필터 역할을 하고 있습니다.

| 계층 | 무엇에 무너지기 쉬운가 | 프로토타입의 방어 방식 |
| --- | --- | --- |
| 사람 | 채팅 도배, 끊임없는 되묻기, 여러 세션의 맥락 기억하기 | 대외 창구는 Router 하나로 통일. 답장은 기본 한 문장(최대 100단어). 접수 확인은 한 번만 발송. 패널에는 사람에게 막혀 있는 티켓만 표시 |
| Router (메인 세션) | 무관한 대화로 컨텍스트가 차거나, 느린 단계에 묶여 전체가 밀리는 것 | 모델 호출 전 코드 단계의 통과 필터. 이미 구독된 Thread는 우회로로 Worker에 직송. 라우팅 메모는 30단어 이내. 능동 평가 외에는 코드나 로그를 읽지 않음 |
| Worker (실행 세션) | 긴 이벤트 텍스트에 컨텍스트가 터지거나, 느린 명령에 묶이는 것 | Inline & Spill: 이벤트 카드는 600자에서 자르고 이어 읽기 포인터를 붙임. 포그라운드 명령은 5초가 지나면 백그라운드로 전환 |

프로토타입 저장소의 `000-philosophy.md` 첫 줄은 꽤 직설적입니다. "Take as little human attention as possible, and give as much value as possible."

글에서는 Fast Path / Slow Path, 배치 처리, 캐시, 투기적 실행, 연산·저장 분리 같은 시스템 공학 개념들을 두루 가져왔지만, 코드에 구현된 모습을 보면 전부 '주의력'(사람의 집중력이든 모델의 제한된 컨텍스트 윈도든)을 아끼는 데 초점이 맞춰져 있습니다. 사람이 수많은 세션을 다 들여다볼 수 없으니 앞에 Router를 세워 문지기 노릇을 맡기고, Router의 전역 컨텍스트가 귀하니 구독 직통과 Worker로 실제 작업 과정의 대화를 빼내고, Worker의 윈도도 긴 로그에는 금방 차 버리니 600자 자르기(Inline & Spill)와 서브에이전트로 한 번 더 걸러 내는 식입니다.

사람이 동시에 챙길 수 있는 일이 서너 개에서 대여섯 개라는 사실은 바뀌지 않으며, Super-agent가 사람의 뇌 용량을 늘려 주지도 못합니다. 바뀌는 건 그 3~5개의 자리를 차지하는 내용물입니다. 예전에는 앞뒤 맥락을 내가 직접 기억하고 있어야 하는 채팅창 3~5개였다면, 이제는 작업이 다 끝나서 고개를 끄덕여 주거나 PR을 승인하기만 하면 되는 티켓 3~5개가 그 자리에 놓입니다.

## 플러그인 생태계 이야기와 로컬 실행 시 주의할 점

이 사이트에서 DeepSeek Harness 플러그인 카탈로그를 운영하다 보니, `dsh-superagent-prototype` 저장소를 열었을 때 가장 먼저 눈이 간 곳은 디렉터리 구조였습니다.

이 프로토타입 자체가 표준 DeepSeek Harness 번들입니다. 루트에 있는 `cordis.patch.yml` 파일 하나가 플러그인들을 연결하고 메인 세션과 실행기용 프리셋을 각각 정의할 뿐, Harness 코어 코드는 단 한 줄도 건드리지 않았습니다. 예전에 「[모든 것은 플러그인이다](/blog/notes/everything-is-a-plugin)」에서 Cordis 번들 구조가 어디까지 확장될 수 있는지 다룬 적이 있는데, 공식 팀이 만든 Super-agent 프로토타입 역시 똑같이 Profile 확장팩 형태로 돌아갑니다.

그리고 며칠 전 올라온 「[DeepSeek Bot 생태계 글](/blog/notes/deepseek-bot-ecosystem)」을 읽으셨다면 반가운 구조가 하나 더 보이셨을 겁니다. 커뮤니티 프로젝트인 Tobs(`@botharness/tobs`)도 단체 채팅방 수신함이 무거운 작업 때문에 멈추는 문제를 풀려고 '상주 Orchestrator 세션 + 백그라운드 Assignment 세션'이라는 2계층 구조를 독자적으로 만들어 냈는데, 이름까지 절반이 겹칩니다. 에이전트를 실제 채팅방에 상주시키며 일을 시키려다 보면 결국 비슷한 아키텍처로 수렴하게 됩니다.

마지막으로, 개인 머신에서 이 프로토타입을 직접 돌려 보려는 분들을 위해 한 가지만 덧붙입니다. 배포 가이드에 적혀 있듯 메인 세션과 실행기 프리셋 모두 기본으로 `danger-full-access`가 켜져 있어서, 현재 OS 사용자 권한으로 별도 승인 없이 명령을 실행합니다. 함께 들어 있는 계정 래퍼 스크립트는 기본 자격 증명만 바꿔 줄 뿐 프로세스를 샌드박스로 격리해 주지는 않습니다. 실제 저장소나 채팅방에 연결해 보실 생각이라면 문서의 권고대로 에이전트 자격 증명만 넣어 둔 제한된 전용 OS 계정을 따로 만들고, 처음에는 허용 목록을 좁게 잡은 뒤 능동 규칙을 기본값인 `observe` 모드로 며칠 돌려 보면서 로그에 어떤 티켓을 수락하려 했는지 확인한 뒤에 차츰 `auto`로 넓혀 가시길 권합니다.
