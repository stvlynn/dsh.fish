モデルのコンテキストウィンドウが 128K から一気に **1,000,000 トークン（1M）** に広がったと聞くと、誰もがまずこう考えます。「もうどのファイルを読むか悩まなくていい。リポジトリ丸ごととスクリーンショットを全部プロンプトに放り込んで、モデルに探させよう」と。

ところが実際のコーディングセッションでそれをやると、15 ターン目あたりで応答が目に見えて遅くなり、同じ画像の再送でペイロードが膨れ上がり、肝心のバグ原因である 3 行のコードが大量のログの中に埋もれてしまいます。

2026 年 4 月 24 日に公開された [DeepSeek-V4 Preview](https://www.deepseek.com/en/news/v4-preview/) で最も注目を集めた数字は「デフォルトで 1M トークン」でした。しかし日常的にエージェントを使う人やプラグイン作者にとって本当に重要だったのは、**その後の数ヶ月間で DeepSeek Harness のアダプターがどう進化したか**です。

![V4 の発表から DeepSeek Harness adapter が段階的に変わった流れ。](/blog/diagrams/v4-adapter-timeline.svg)

## 2 つのオープンウェイトモデルと標準 1M コンテキスト

まずは 4 月の発表内容を整理しましょう。

DeepSeek は 1M コンテキストを別料金の特別プランにするのではなく、**トークン単位の圧縮と DSA（DeepSeek Sparse Attention）** によって、2 つの MoE モデルの**標準ウィンドウ**として提供しました。

| モデル | 総パラメータ / 活性パラメータ | API の `model` 名 | 主な役割 |
| --- | --- | --- | --- |
| **DeepSeek-V4-Pro** | 1.6T / 49B | `deepseek-v4-pro` | 複雑な設計、複数ファイルにまたがるデバッグ、数学・深い推論（`thinking: max` 推奨） |
| **DeepSeek-V4-Flash** | 284B / 13B | `deepseek-v4-flash` | 高速な反復作業、サブエージェントのタスク、低コストな日常のツールループ |

どちらも既存の `base_url` をそのまま使い、思考（thinking）モードと非思考モードの両方をサポートします（Web やアプリでは **Expert Mode / Instant Mode** として表示されます）。エージェント用途では思考強度を `max` に設定することが推奨されています。

もう一つ見逃せないのが旧モデル名の廃止日です。**`deepseek-chat` と `deepseek-reasoner` は 2026 年 7 月 24 日 15:59 UTC をもって廃止**されました。それ以前は V4-Flash への一時的なエイリアスとして動いていましたが、廃止日以降は完全に無効な文字列となっています。

## DeepSeek Harness が 4 月の発表をどう実装に落とし込んだか

モデルの発表は「重みが何をできるか」を示しますが、エージェントランタイムはそれを「安定したツール実行」に変えなければなりません。

8 月の `v0.1.2-alpha.1` に至るリリース履歴をたどると、公式アダプターが段階적으로 V4 対応を固めていった過程がよく分かります。

1. **ネイティブ画像リクエストの有効化（`v0.1.0-rc.8`）：** `/goal`、`/plan`、および `@` によるファイル・セッション参照でネイティブな画像送信が可能になりました。
2. **実験的ビジョンモデルの追加（`v0.1.1-rc.1`）：** 公式アダプターに `DeepSeek-V4-Flash-Vision-Exp`（`deepseek-v4-flash-vision-exp`）が追加され、スクリーンショットや図を入力できるようになりました。
3. **Files API による再利用と自動リサイズ（`v0.1.1-rc.2`）：** 毎ターン同じ画像を Base64 で送り直すのではなく、**Files API** に一度アップロードしたファイル ID を再利用し、モデルに合わせて自動リサイズ・変換するようになりました。
4. **プラグイン識別子と画像を考慮したコンパクション（`v0.1.2-alpha.1`）：** セッションのコンパクション（要約圧縮）で画像トークンも計算対象に入り、公式リクエストに有効なプラグイン名とバージョンが添付されるようになりました。

*（最新ビルドをお使いの方への補足：続編の「[DeepSeek-V4.1-Flash とネイティブ検索](/blog/deepseek/v4-1-flash-and-search)」で詳しく解説している通り、2026 年 9 月の `v0.1.5` でネイティブ視覚機能は `deepseek-flash` に統合され、`deepseek-v4-flash-vision-exp` は役割を終えました。一方、`deepseek-v4-pro`（`DeepSeek-V4-Pro-0813`）は引き続き重い推論向けの個別モデルとして提供されています。）*

## 1M コンテキストになっても「検索と絞り込み」が不要にならない理由

1M ウィンドウを手にした開発者が陥りやすい罠があります。それは**「枠が広がったからといって、無駄なコンテキストがタダになるわけではない」**ということです。

100 万トークンまで切り詰められずに保持できるとしても、次の 3 つは変わりません。

- **毎ターンの入力トークンには遅延とコストがかかります。** エージェントは何十ステップもループを回すため、履歴が膨らむほど毎ステップの応答待ち時間が増えていきます。
- **ノイズはモデルの注意力を奪います。** 無関係なログを大量に流し込むと、本当に重要な数行の差分が埋もれてしまいます。
- **画像にも予算管理が必要です。** Files API はアップロードの重複を防ぎますが、「ほぼ同じ画面のスクリーンショット 10 枚」が本当に必要かどうかまでは判断してくれません。プラグイン側で重複画像を間引いてから返す設計が重要です。

## プラグイン作者とユーザーのための移行チェックリスト

設定ファイルやプラグインの README を点検する際は、次の対応表を基準にしてください。

```text
廃止された旧名称（7/24 停止）   8月 V4 時点のモデル名     現在の推奨モデル名（2026年9〜10月）
----------------------------   ------------------       ------------------------------------
deepseek-chat               -> deepseek-v4-flash     -> deepseek-flash（テキスト + ネイティブ視覚）
deepseek-reasoner           -> deepseek-v4-pro       -> deepseek-v4-pro（DeepSeek-V4-Pro-0813）
```

1. **README やサンプルから `deepseek-chat` と `deepseek-reasoner` を削除する。** 2026 年 7 月 24 日以降、これらの名前は動作しません。`dsh.fish` では、廃止されたモデル名を案内し続けている README はメンテナンス上の減点対象となります。
2. **「リポジトリ丸ごと投入」ではなく、根拠を絞る設計にする。** 1M の枠は、長いデバッグセッションで重要な設計判断や差分を保持するために使いましょう。
3. **画像を第一級のツール結果として扱う。** スクリーンショットやグラフを生成するプラグインは、Files API とコンパクションが正しく機能するよう重複を除いた画像を返してください。
4. **モデルの選択権はユーザーの Profile に委ねる。** `dsh.fish` のインストール計画は API キーを書き込まず、モデルも固定しません。
