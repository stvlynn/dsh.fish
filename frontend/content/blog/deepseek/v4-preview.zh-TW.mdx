當大模型的上下文視窗從 128K 一夜之間跳升到 **1,000,000 Token（1M）** 時，幾乎所有人都會產生同一個衝動：以後再也不用費心篩選檔案了，直接把整個程式碼儲存庫塞進提示詞，把所有截圖一股腦丟給模型，讓它自己去找答案！

然而當你真正在程式碼工作階段裡這麼做時，到了第十五輪工具呼叫，回應延遲開始明顯拉長，重複上傳的截圖讓請求體急速膨脹，而真正引發 Bug 的那三行程式碼早已被淹沒在幾萬行無關日誌裡。

2026 年 4 月 24 日，DeepSeek 發佈了 [DeepSeek-V4 Preview（V4 預覽版）](https://www.deepseek.com/news/v4-preview/)。公告最吸睛的數字無疑是「預設 1M 上下文視窗」；但對於一般使用者與外掛開發者來說，真正關鍵的是**隨後幾個月裡 DeepSeek Harness 在底層介面卡上做出的連續改造**——正是這些改造，才讓智慧體真正用好了 1M 視窗、透過 Files API 高效重用圖片，並平穩完成了舊模型名稱的退役交接。

## 兩款開源權重模型，同一個預設 1M 視窗

我們先用最通俗的語言梳理一下 4 月份的 V4 公告到底發佈了什麼。

DeepSeek 沒有把長上下文做成一個額外收費的「長文本高價版」，而是依靠**逐 Token 壓縮（token-wise compression）與 DSA（DeepSeek 稀疏注意力，DeepSeek Sparse Attention）**，直接把 **1M Token 設為兩款 MoE 模型的預設標準視窗**：

| 模型名稱 | 總參數 / 激活參數 | API `model` 標識 | 適用場景定位 |
| --- | --- | --- | --- |
| **DeepSeek-V4-Pro** | 1.6T 總參數 / 49B 激活 | `deepseek-v4-pro` | 複雜架構設計、跨多檔案疑難排錯、數學與深度推理（推薦開啟 `thinking: max`） |
| **DeepSeek-V4-Flash** | 284B 總參數 / 13B 激活 | `deepseek-v4-flash` | 高頻工具呼叫、子智慧體並行任務與日常快速迭代，成本與延遲大幅降低 |

兩款模型均沿用原有的 API `base_url`，並同時支援思考（thinking）與非思考模式（在網頁端與 App 中對應**專家模式 Expert Mode** 與**極速模式 Instant Mode**）。對於智慧體（Agent）負載，官方明確建議將思考強度設為 `max`。

同樣需要畫重點的是舊名稱的退役時間表：老一代的 **`deepseek-chat` 與 `deepseek-reasoner` 已於 UTC 時間 2026 年 7 月 24 日 15:59 正式停止服務**。在此日期前它們曾臨時路由至 V4-Flash，而在那之後，這兩個字串已經徹底失效，不再作為別名保留。

## DeepSeek Harness 是如何把模型能力變成執行期底座的？

模型公告告訴你權重能做什麼，而智慧體執行期（Harness）必須把這些能力變成穩定可靠的工具呼叫。

順著 8 月份 `v0.1.2-alpha.1` 之前的版本脈絡往回看，你會看到官方介面卡分四個階段完成了對 V4 的深度適配：

1. **打通原生圖片請求（`v0.1.0-rc.8`）：** 在 `/goal`、`/plan` 以及 `@` 檔案與工作階段引用中正式啟用了原生圖片請求。
2. **引入實驗性視覺模型（`v0.1.1-rc.1`）：** 官方介面卡新增 `DeepSeek-V4-Flash-Vision-Exp`（`deepseek-v4-flash-vision-exp`），讓智慧體可以直接看懂截圖與架構圖。
3. **優先走 Files API 重用圖片並自動縮放（`v0.1.1-rc.2`）：** 不再每輪對話都重複上傳幾 MB 的 Base64 圖片資料，而是優先透過 **Files API** 上傳並在後續輪次重用檔案 ID，同時自動按模型要求縮放與轉換圖片格式。
4. **外掛標識與圖片壓縮計費（`v0.1.2-alpha.1`）：** 在工作階段自動壓縮（Compaction）時將圖片納入預算統計，並在官方請求中附帶已啟用外掛的套件名與版本。

*（給使用最新版本的讀者的提示：正如我們在後續文章《[DeepSeek-V4.1-Flash 與原生搜尋](/blog/deepseek/v4-1-flash-and-search)》中所介紹的，2026 年 9 月發佈的 `v0.1.5` 已將原生多模態視覺直接合入了 `deepseek-flash`，原先獨立的 `deepseek-v4-flash-vision-exp` 已完成歷史使命並自動路由過去；而 `deepseek-v4-pro`（`DeepSeek-V4-Pro-0813`）則繼續作為獨立的重度推理模型提供服務。）*

## 為什麼擁有 1M 視窗後，依然不能放棄精準檢索？

很多初次接觸 1M 上下文的開發者容易掉進一個誤區：**視窗變大了，不等於塞進提示詞裡的冗餘內容是免費的。**

即便模型能夠裝下 100 萬 Token 而不報錯截斷，你依然要面對三個現實物理規律：

- **每一輪重讀歷史都要付出延遲和費用。** 智慧體一個任務往往要連續呼叫十幾次工具，歷史越臃腫，每一步的首字延遲（TTFT）和開銷就越高。
- **無關雜訊會稀釋注意力。** 如果一個搜尋外掛不分青紅皂白把 8 萬 Token 的原始日誌倒進上下文，模型在後續每一輪都得在這堆草垛裡找針。
- **視覺輸入同樣需要預算管理。** Files API 解決了「同一張圖不重複上傳」的頻寬問題，自動縮放解決了解析度超標問題，但它們無法替你判斷「連續十張幾乎一模一樣的網頁截圖」到底有沒有留存價值。優秀的外掛應當在傳回結果前先對圖片去重。

## 一般使用者與外掛作者的四步遷移清單

如果你正在設定自己的 Profile，或者在 `dsh.fish` 上維護外掛與技能（Skill），請對照以下表格完成檢查：

```text
已退役舊名稱（7月24日停用）   8月 V4 階段模型名         目前推薦模型名（2026年9月–10月）
--------------------------   ------------------       ------------------------------------
deepseek-chat             -> deepseek-v4-flash     -> deepseek-flash（文本 + 原生多模態視覺）
deepseek-reasoner         -> deepseek-v4-pro       -> deepseek-v4-pro（DeepSeek-V4-Pro-0813）
```

1. **立即清理 README 與設定範例中的 `deepseek-chat` 和 `deepseek-reasoner`。** 這兩個名字在 2026 年 7 月 24 日之後就已徹底停用。在 `dsh.fish` 的評分體系中，仍然教使用者設定失效模型名的文件會被判定為維護缺陷。
2. **用「精選證據」代替「全庫傾倒」。** 把 1M 視窗用來保存跨檔案的核心架構上下文和關鍵 Diff，而不是放棄檢索策略。
3. **把圖片當作一等公民工具結果。** 如果你的外掛會產出圖表、截圖或視覺對比，請確保傳回乾淨、去重後的檔案，以便官方介面卡透過 Files API 快取並在壓縮時準確計入預算。
4. **把模型選擇權留給使用者的 Profile。** `dsh.fish` 的安裝計畫從不寫入 API 金鑰，也不會替使用者寫死計費模型。讓使用者根據任務需要自行在 `deepseek-v4-pro` 與 `deepseek-flash` 之間切換。
