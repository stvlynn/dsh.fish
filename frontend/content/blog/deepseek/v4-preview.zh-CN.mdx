当大模型的上下文窗口从 128K 一夜之间跳升到 **1,000,000 Token（1M）** 时，几乎所有人都会产生同一个冲动：以后再也不用费心筛选文件了，直接把整个代码仓库塞进提示词，把所有截图一股脑丢给模型，让它自己去找答案！

然而当你真正在代码会话里这么干时，到了第十五轮工具调用，响应延迟开始明显拉长，重复上传的截图让请求体急速膨胀，而真正引发 Bug 的那三行代码早已被淹没在几万行无关日志里。

2026 年 4 月 24 日，DeepSeek 发布了 [DeepSeek-V4 Preview（V4 预览版）](https://www.deepseek.com/news/v4-preview/)。公告最吸睛的数字无疑是“默认 1M 上下文窗口”；但对于普通用户和插件开发者来说，真正关键的是**随后几个月里 DeepSeek Harness 在底层适配器上做出的连续改造**——正是这些改造，才让智能体真正用好了 1M 窗口、通过 Files API 高效复用图片，并平稳完成了旧模型名称的退役交接。

![V4 公告之后，DeepSeek Harness adapter 分阶段发生变化。](/blog/diagrams/v4-adapter-timeline.svg)

## 两款开源权重模型，同一个默认 1M 窗口

我们先用最通俗的语言梳理一下 4 月份的 V4 公告到底发布了什么。

DeepSeek 没有把长上下文做成一个额外收费的“长文本高价版”，而是依靠**逐 Token 压缩（token-wise compression）与 DSA（DeepSeek 稀疏注意力，DeepSeek Sparse Attention）**，直接把 **1M Token 设为两款 MoE 模型的默认标准窗口**：

| 模型名称 | 总参数 / 激活参数 | API `model` 标识 | 适用场景定位 |
| --- | --- | --- | --- |
| **DeepSeek-V4-Pro** | 1.6T 总参数 / 49B 激活 | `deepseek-v4-pro` | 复杂架构设计、跨多文件疑难排错、数学与深度推理（推荐开启 `thinking: max`） |
| **DeepSeek-V4-Flash** | 284B 总参数 / 13B 激活 | `deepseek-v4-flash` | 高频工具调用、子智能体并发任务与日常快速迭代，成本与延迟大幅降低 |

两款模型均沿用原有的 API `base_url`，并同时支持思考（thinking）与非思考模式（在网页端与 App 中对应**专家模式 Expert Mode** 与**极速模式 Instant Mode**）。对于智能体（Agent）负载，官方明确建议将思考强度设为 `max`。

同样需要划重点的是旧名称的退役时间表：老一代的 **`deepseek-chat` 与 `deepseek-reasoner` 已于 UTC 时间 2026 年 7 月 24 日 15:59 正式停止服务**。在此日期前它们曾临时路由至 V4-Flash，而在那之后，这两个字符串已经彻底失效，不再作为别名保留。

## DeepSeek Harness 是如何把模型能力变成运行时底座的？

模型公告告诉你权重能做什么，而智能体运行时（Harness）必须把这些能力变成稳定可靠的工具调用。

顺着 8 月份 `v0.1.2-alpha.1` 之前的版本脉络往回看，你会看到官方适配器分四个阶段完成了对 V4 的深度适配：

1. **打通原生图片请求（`v0.1.0-rc.8`）：** 在 `/goal`、`/plan` 以及 `@` 文件与会话引用中正式启用了原生图片请求。
2. **引入实验性视觉模型（`v0.1.1-rc.1`）：** 官方适配器新增 `DeepSeek-V4-Flash-Vision-Exp`（`deepseek-v4-flash-vision-exp`），让智能体可以直接看懂截图与架构图。
3. **优先走 Files API 复用图片并自动缩放（`v0.1.1-rc.2`）：** 不再每轮对话都重复上传几兆的 Base64 图片数据，而是优先通过 **Files API** 上传并在后续轮次复用文件 ID，同时自动按模型要求缩放与转换图片格式。
4. **插件标识与图片压缩计费（`v0.1.2-alpha.1`）：** 在会话自动压缩（Compaction）时将图片纳入预算统计，并在官方请求中附带已启用插件的包名与版本。

*（给使用最新版本的读者的提示：正如我们在后续文章《[DeepSeek-V4.1-Flash 与原生搜索](/blog/deepseek/v4-1-flash-and-search)》中所介绍的，2026 年 9 月发布的 `v0.1.5` 已将原生多模态视觉直接合入了 `deepseek-flash`，原先独立的 `deepseek-v4-flash-vision-exp` 已完成历史使命并自动路由过去；而 `deepseek-v4-pro`（`DeepSeek-V4-Pro-0813`）则继续作为独立的重度推理模型提供服务。）*

## 为什么拥有 1M 窗口后，依然不能放弃精准检索？

很多初次接触 1M 上下文的开发者容易掉进一个误区：**窗口变大了，不等于塞进提示词里的冗余内容是免费的。**

即便模型能够装下 100 万 Token 而不报错截断，你依然要面对三个现实物理规律：

- **每一轮重读历史都要付出延迟和费用。** 智能体一个任务往往要连续调用十几次工具，历史越臃肿，每一步的首字延迟（TTFT）和开销就越高。
- **无关噪音会稀释注意力。** 如果一个搜索插件不分青红皂白把 8 万 Token 的原始日志倒进上下文，模型在后续每一轮都得在这堆草垛里找针。
- **视觉输入同样需要预算管理。** Files API 解决了“同一张图不重复上传”的带宽问题，自动缩放解决了分辨率超标问题，但它们无法替你判断“连续十张几乎一模一样的网页截图”到底有没有留存价值。优秀的插件应当在返回结果前先对图片去重。

## 普通用户与插件作者的四步迁移清单

如果你正在配置自己的 Profile，或者在 `dsh.fish` 上维护插件与技能（Skill），请对照以下表格完成检查：

```text
已退役旧名称（7月24日停用）   8月 V4 阶段模型名         当前推荐模型名（2026年9月–10月）
--------------------------   ------------------       ------------------------------------
deepseek-chat             -> deepseek-v4-flash     -> deepseek-flash（文本 + 原生多模态视觉）
deepseek-reasoner         -> deepseek-v4-pro       -> deepseek-v4-pro（DeepSeek-V4-Pro-0813）
```

1. **立即清理 README 与配置示例中的 `deepseek-chat` 和 `deepseek-reasoner`。** 这两个名字在 2026 年 7 月 24 日之后就已彻底停用。在 `dsh.fish` 的评分体系中，仍然教用户配置失效模型名的文档会被判定为维护缺陷。
2. **用“精选证据”代替“全库倾倒”。** 把 1M 窗口用来保存跨文件的核心架构上下文和关键 Diff，而不是放弃检索策略。
3. **把图片当作一等公民工具结果。** 如果你的插件会产出图表、截图或视觉对比，请确保返回干净、去重后的文件，以便官方适配器通过 Files API 缓存并在压缩时准确计入预算。
4. **把模型选择权留给用户的 Profile。** `dsh.fish` 的安装计划从不写入 API 密钥，也不会替用户硬编码计费模型。让用户根据任务需要自行在 `deepseek-v4-pro` 与 `deepseek-flash` 之间切换。
