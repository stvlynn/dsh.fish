모델의 컨텍스트 윈도우가 128K에서 하루아침에 **1,000,000 토큰(1M)**으로 넓어졌다는 소식을 들으면 누구나 같은 유혹을 느낍니다. "이제 어떤 파일을 읽을지 고민할 필요 없겠다. 저장소 전체와 스크린샷을 전부 프롬프트에 밀어 넣고 모델이 알아서 찾게 하자!"

하지만 실제 코딩 세션에서 그렇게 해 보면 15번째 턴쯤부터 응답 지연이 눈에 띄게 길어지고, 매번 다시 올라가는 스크린샷 때문에 요청 크기가 불어나며, 정작 버그를 일으킨 세 줄짜리 코드는 수만 줄의 로그 속에 파묻혀 버립니다.

2026년 4월 24일 공개된 [DeepSeek-V4 Preview](https://www.deepseek.com/en/news/v4-preview/)에서 가장 눈길을 끈 숫자는 '기본 1M 컨텍스트'였습니다. 하지만 일반 사용자와 플러그인 제작자에게 진짜 중요했던 사건은 그다음에 일어났습니다. **DeepSeek Harness가 여름 내내 공식 어댑터를 손보며 1M 윈도우와 Files API 이미지 재사용, 그리고 구형 모델 이름 퇴역을 실제 런타임에 녹여낸 과정**입니다.

![V4 발표 이후 DeepSeek Harness adapter가 단계적으로 바뀐 흐름.](/blog/diagrams/v4-adapter-timeline.svg)

## 두 개의 오픈 웨이트 모델, 하나의 기본 1M 윈도우

먼저 4월 발표가 실제로 무엇을 내놓았는지 쉽게 짚어 보겠습니다.

DeepSeek는 긴 컨텍스트를 별도 요금제로 파는 대신, **토큰 단위 압축(token-wise compression)과 DSA(DeepSeek Sparse Attention)**를 통해 두 오픈 웨이트 MoE 모델 모두에서 **1M 토큰을 기본 윈도우**로 제공했습니다.

| 모델 | 전체 / 활성 파라미터 | API `model` 문자열 | 적합한 작업 |
| --- | --- | --- | --- |
| **DeepSeek-V4-Pro** | 1.6T 전체 / 49B 활성 | `deepseek-v4-pro` | 복잡한 아키텍처 설계, 다중 파일 디버깅, 수학 및 심층 추론(`thinking: max` 권장) |
| **DeepSeek-V4-Flash** | 284B 전체 / 13B 활성 | `deepseek-v4-flash` | 빠른 반복 작업, 서브에이전트 위임 작업, 저렴하고 빠른 일상 도구 루프 |

두 모델 모두 기존 `base_url`을 그대로 쓰며 추론(thinking) 모드와 일반 모드를 모두 지원합니다(웹과 앱에서는 **Expert Mode / Instant Mode**로 표시됩니다). 에이전트 워크로드에서는 추론 강도를 `max`로 설정하는 것이 권장됩니다.

그못지않게 중요한 것이 구형 모델 이름의 종료 일정이었습니다. **`deepseek-chat`과 `deepseek-reasoner`는 2026년 7월 24일 15:59 UTC에 공식 종료**되었습니다. 그전까지는 V4-Flash로 연결되는 임시 별칭 역할을 했지만, 종료일 이후로는 더 이상 작동하지 않는 죽은 문자열이 되었습니다.

## DeepSeek Harness는 V4 발표를 어떻게 런타임 기능으로 바꿨을까?

모델 발표가 가중치의 잠재력을 보여준다면, 에이전트 런타임은 이를 안정적인 도구 호출로 구현해야 합니다.

8월 `v0.1.2-alpha.1`까지 이어진 DeepSeek Harness의 릴리스 기록을 따라가 보면 공식 어댑터가 어떻게 V4를 흡수했는지 한눈에 보입니다.

1. **네이티브 이미지 요청 활성화(`v0.1.0-rc.8`):** `/goal`, `/plan`, 그리고 `@` 파일·세션 참조에서 네이티브 이미지 요청이 켜졌습니다.
2. **실험적 비전 모델 추가(`v0.1.1-rc.1`):** 공식 어댑터에 `DeepSeek-V4-Flash-Vision-Exp`(`deepseek-v4-flash-vision-exp`)가 추가되어 스크린샷과 다이어그램을 직접 입력할 수 있게 되었습니다.
3. **Files API 업로드 재사용 및 자동 리사이즈(`v0.1.1-rc.2`):** 매 턴마다 무거운 Base64 이미지를 다시 올리는 대신 **Files API**를 우선 사용하여 업로드된 파일 ID를 재사용하고, 모델 요구사항에 맞춰 자동으로 크기를 조절·변환합니다.
4. **플러그인 식별 헤더 및 이미지 컴팩션 반영(`v0.1.2-alpha.1`):** 세션 컴팩션(요약 압축) 시 이미지 토큰을 함께 계산하고, 공식 요청에 활성 플러그인의 패키지 이름과 버전을 첨부합니다.

*(최신 버전을 쓰는 분들을 위한 참고: 후속 글인 [DeepSeek-V4.1-Flash와 네이티브 검색](/blog/deepseek/v4-1-flash-and-search)에서 다루듯, 2026년 9월 `v0.1.5`부터는 네이티브 비전이 `deepseek-flash`에 직접 통합되면서 별도의 `deepseek-v4-flash-vision-exp` 문자열은 은퇴했습니다. 한편 `deepseek-v4-pro`(`DeepSeek-V4-Pro-0813`)는 무거운 추론을 위한 별도 모델로 계속 제공됩니다.)*

## 1M 윈도우가 생겨도 여전히 '선별과 검색'이 필요한 이유

처음 1M 컨텍스트를 접할 때 빠지기 쉬운 함정이 있습니다. **창이 넓어졌다고 해서 무분별하게 채워 넣은 컨텍스트가 공짜가 되지는 않는다**는 점입니다.

100만 토큰이 잘리지 않고 들어간다 해도 다음 세 가지는 그대로입니다.

- **매 턴마다 읽는 입력 토큰은 여전히 지연 시간과 비용을 발생시킵니다.** 에이전트는 한 작업을 위해 수십 번 루프를 돌기 때문에 히스토리가 비대해질수록 매 단계 응답이 느려집니다.
- **불필요한 로그는 모델의 집중력을 떨어뜨립니다.** 검색 도구가 8만 토큰짜리 날것의 로그를 그대로 쏟아부으면 모델은 매 턴마다 건초더미에서 바늘을 찾아야 합니다.
- **시각 입력에도 예산 관리가 필요합니다.** Files API가 중복 업로드를 막아 주고 자동 리사이즈가 해상도를 맞춰 주지만, '거의 똑같은 화면 스크린샷 10장'이 모두 필요한지는 판단해 주지 않습니다. 좋은 플러그인은 결과를 반환하기 전에 중복 이미지를 먼저 걸러냅니다.

## 사용자와 플러그인 제작자를 위한 마이그레이션 체크리스트

프로필을 구성하거나 `dsh.fish`에 플러그인·스킬을 배포하고 있다면 아래 표를 기준으로 점검해 보세요.

```text
종료된 구형 이름(7/24 중단)     8월 V4 모델 이름          현재 권장 모델 이름(2026년 9~10월)
--------------------------     ------------------       ------------------------------------
deepseek-chat               -> deepseek-v4-flash     -> deepseek-flash(텍스트 + 네이티브 비전)
deepseek-reasoner           -> deepseek-v4-pro       -> deepseek-v4-pro(DeepSeek-V4-Pro-0813)
```

1. **README와 예제에서 `deepseek-chat`과 `deepseek-reasoner`를 지우세요.** 2026년 7월 24일 이후로 이 이름들은 작동하지 않습니다. `dsh.fish`에서는 이미 죽은 모델 이름을 안내하는 문서를 유지보수 결함으로 감점합니다.
2. **저장소 통째 덤프 대신 정밀한 근거 수집으로 설계하세요.** 1M 윈도우는 긴 디버깅 세션 동안 핵심 아키텍처 맥락과 다중 파일 Diff를 유지하는 데 써야 합니다.
3. **이미지를 일급 도구 결과로 다루세요.** 스크린샷이나 플롯을 생성하는 플러그인이라면 Files API 캐시와 컴팩션이 효율적으로 작동하도록 중복을 제거한 깔끔한 이미지를 반환하세요.
4. **모델 선택권은 사용자의 Profile에 맡기세요.** `dsh.fish`의 설치 계획은 절대 API 키를 쓰거나 특정 과금 모델을 강제하지 않습니다.
