Have you ever followed a documentation page to install a package, only to discover that the CLI tool uses different flags and the AI agent reading the site's `/llms.txt` is looking at a stale copy from three weeks ago?

As soon as a developer hub serves both human readers in a browser and autonomous agents in a terminal, "split-brain" drift becomes the default failure mode. A hardcoded scoring weight in a docs table disagrees with the backend API; a retired plugin category stays alive in a sidebar; an in-session plugin installs slightly differently than the web UI.

Everything we shipped on `dsh.fish` through 29 August 2026 was designed around a single engineering rule: **every surface—whether for a human, a CLI client, or an LLM—must read from the same canonical source of truth.** Here is what changed and how you can use each surface today.

![The catalog now feeds human, install-client, web, and agent-facing surfaces from shared sources.](/blog/diagrams/hub-surfaces.svg)

## Product docs graduated from a single tab to a six-locale guide tree

Originally, `/docs` was a single React page with tabs for each artifact kind. That worked when the catalog only needed a 200-word summary, but it broke down the moment someone needed a step-by-step walkthrough for publishing a bundle, using the CLI, or understanding how quality scores are computed.

We rebuilt `/docs` as a dedicated Fumadocs section compiled at build time across all six locales (`en`, `zh-CN`, `zh-TW`, `ja`, `ko`, `ru`):

- **Task-focused guides:** Separate guides now cover the quickstart, core concepts, each of the four publish formats, the CLI (`@dsh-fish/cli`), the in-session hub plugin (`@dsh-fish/hub`), submission, scoring, and the REST API.
- **Live scoring weights, never copy-pasted numbers:** Instead of hardcoding weights in prose where they can go stale, the scoring documentation tables query `GET /api/v1/scoring` directly.
- **Dedicated docs search:** Documentation search runs at `/docs/search`, keeping `/api/*` reserved for our Hono backend routes.

## Installing without leaving your Harness session: `@dsh-fish/hub`

Browsing a catalog in a web tab is great for discovery, but when you are already deep inside a DeepSeek Harness session, switching windows to copy commands interrupts your flow.

In August, we published **`@dsh-fish/hub`** to npm as a native Cordis plugin you can load directly inside a running DeepSeek Harness profile:

1. **In-session tools and UI:** It searches the catalog (`hub_search`), inspects artifact details (`hub_show`), opens READMEs, and executes the exact same install plans (`hub_install`, `hub_remove`, `hub_update`) that the website displays.
2. **Reliable device-grant sign-in:** We fixed the browser `Authorize` handoff so approving a device login in your browser cleanly redeems the token (`$DSH_HOME/.dsh-fish-token.json`) that the CLI or plugin is polling for.
3. **Native settings integration:** The plugin registers its configuration through the Harness plugin settings client and ships with npm 11 trusted publishing.

## Pruning catalog fiction: why two kinds were retired

When we audited our initial catalog taxonomy against what DeepSeek Harness actually loads at boot, two categories stood out as mistakes: `mcp-server` and `hook-bridge`.

Neither one is a standalone unit that `dsh` loads on its own. An MCP server or a hook is packaged *inside* a Bundle or a Profile. Keeping them as top-level catalog kinds meant showing users an "Install" button for a format the runtime did not recognize.

We removed both kinds and configured `301` permanent redirects:

- Old `/kind/mcp-server` and `/kind/hook-bridge` URLs now redirect cleanly to `/browse`.
- Their old publishing tabs redirect to `/docs/plugins`.
- The catalog now indexes only the **four real Harness kinds**: `bundle`, `skill`, `agent-preset`, and `profile`, with browse categories aligned to [awesome-dsh-plugin.com](https://awesome-dsh-plugin.com).

## First-class delivery for AI agents (`llms.txt` and Markdown negotiation)

When an AI agent visits a documentation site, feeding it a 200KB HTML app shell full of navigation chrome wastes tokens and obscures the text.

Every page on `dsh.fish` now speaks Markdown natively alongside HTML. Step through the interactive mock UI below to see how all four surfaces stay synchronized:

Here is what an agent or script can fetch right now:

- **Discovery maps:** `/llms.txt` at the site root, `/docs/llms.txt` (and `/docs/llms-full.txt` as a single-file concatenation) for product guides, and `/blog/llms.txt` plus `/blog/feed.xml` (Atom) for editorial posts.
- **Direct Markdown negotiation:** Append `.md` to any guide or blog URL (such as `/docs/cli.md` or `/blog/index.md`), or send `Accept: text/markdown` on the canonical URL. Even a `404` with `Accept: text/markdown` returns a concise Markdown recovery map instead of an HTML error page.
- **Zero-flicker localized READMEs:** When a plugin updates its README, our background translation pipeline keeps the previous completed translation visible until the new one finishes, so localized pages never flash blank mid-update.

## Which surface should you reach for?

Pick the tool that matches where you are working:

- **Learning how to package or score a plugin:** Start at [`/docs`](/docs).
- **Pointing an LLM or coding agent at our guides:** Hand it `/docs/llms.txt` or `/blog/llms.txt`.
- **Inspecting and installing from a terminal:** Run `npx @dsh-fish/cli show <id>` and `npx @dsh-fish/cli add <id> --profile web`.
- **Adding capabilities mid-conversation inside DeepSeek Harness:** Install `@dsh-fish/hub`.
