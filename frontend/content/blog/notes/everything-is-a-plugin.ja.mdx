普段使っているコードエディタに拡張機能を入れたところ、突然ターミナルが動かなくなったり、モデル設定が勝手に書き換わったりした経験はないでしょうか。原因を調べようとしても、エディタ本体が巨大なブラックボックスになっていて、拡張機能が外側から無理やり貼り付けられているだけだと気づくことは少なくありません。

では、発想を逆転させてみましょう。もしアプリケーションの「コア」がほとんど空っぽだったらどうなるでしょうか？チャット画面も、Bash ツールも、モデルへの接続も、さらにはエージェントの思考ループそのものまで、サードパーティ製の拡張機能とまったく同じ仕組みで読み込まれるとしたら？

それこそが、[DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness)（`dsh`）の README が冒頭で掲げる **everything is a plugin（すべてはプラグイン）** という言葉の本当の意味です。これはマーケットプレイス向けのキャッチコピーではなく、合成ランタイム [Cordis](https://github.com/cordiverse/cordis)（論文 [_A Programming Paradigm for Spatiotemporal Composability_](https://arxiv.org/abs/2608.25512)）に基づくアーキテクチャ上の原則です。

この原則がディスク上でどう動いているかが分かると、DeepSeek Harness とこのカタログ（`dsh.fish`）のつながりが一気に見えてきます。手元のフォルダから起動中のセッションまで、順番にたどってみましょう。

![Profile がカタログ artifact を一つの権限制約付き Harness session に構成する流れ。](/blog/diagrams/plugin-composition.svg)

## A profile is the unit that boots

プラグインの話に入る前に、ターミナルで `npx @deepseek-ai/dsh web` と入力したとき、内部で何が起きているのかを見てみましょう。

エージェントはどこにデータを保存するのでしょうか？デフォルトでは `~/.dsh`（または `$DSH_HOME` で指定したパス）にホームディレクトリが作られ、その中に `profiles/` というフォルダが用意されます。

**Profile**（`$DSH_HOME/profiles/<name>`）は、エージェントを動かすための「レシピ一式」だと考えてください。どの npm パッケージを読み込み、どの設定パッチ（`cordis.patch.yml`）を当てるかがそこに記録されています。

`dsh` を起動するときは、常にいずれかの Profile を起動しています。

- `dsh web` は `web` Profile を起動します（`http://127.0.0.1:3080` のブラウザ UI）。
- `dsh --profile headless` はサーバーを持たない単発実行用の CLI ランナーを起動します。
- `dsh --profile sdk` や `dsh --profile acp` は、Python/TypeScript SDK や外部ツール向けのプロトコルサーバーを起動します。

Profile を通さずに別のスタックを読み込む裏口はありません。だからこそ、「とりあえず DeepSeek Harness 本体にプラグインを入れる」という曖昧な操作は存在しないのです。どの Profile に入れるかを決めないインストールは、宛先のない手紙と同じです。

## シンプルなものから順に並べる 4 つの構成単位

Profile が起動単位だとすると、その中にはどんな材料を入れられるのでしょうか？

`dsh.fish` には 4 つの種類（Kind）しかありません。これはカタログ側で勝手に作った分類ではなく、DeepSeek Harness が実際に読み込める 4 つの単位そのものです。

| 種類（Kind）         | こんなときに選ぶ                                      | DeepSeek Harness での読み込み方                                                                 |
| ------------ | ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| **Skill**        | Markdown だけで再利用可能な手順や知識をモデルに教えたいとき           | `$DSH_HOME/skills/<name>/SKILL.md` に配置され、モデルが必要に応じて読み込む                |
| **Agent preset** | 役割・プロンプトの前後付け・ツール構成をひとまとめにしたいとき   | `agent.cordis.yml` で定義（新しい Harness では Bundle として配布・管理）        |
| **Bundle**       | コードで新しいツール、UI パネル、モデルアダプターを追加したいとき | `package.json` に `dsh.bundle` を持つ npm パッケージ。`dsh plugin add` で Profile に追加する            |
| **Profile**      | 複数の Bundle を組み合わせた完成済み環境をそのまま共有したいとき      | `@deepseek-ai/dsh-base` の上に順番に適用される Bundle のリスト（`dsh.profile.bundles`）  |

以前このカタログにあった `mcp-server` と `hook-bridge` は廃止され、現在は `/browse` へ `301` リダイレクトされています。理由は単純で、Harness 側にそのような名前の読み込みスロットが存在しなかったからです。MCP サーバーやフックは Bundle や Profile の一部として提供されます。ランタイムが直接読み込めない分類を残しておくと、利用者が迷う原因になってしまいます。

## なぜワンライナーの即時実行ではなく「インストール計画」なのか

多くのツールでは、拡張機能の導入は「コマンドを貼り付けて Enter を押し、壊れないことを祈る」作業になりがちです。しかし DeepSeek Harness は Profile のレイヤー合成で動くため、`dsh.fish` では**実行前に変更内容を読めるインストール計画（Install Plan）**を中心据えました。

Web サイトで見ても、ターミナルの `npx @dsh-fish/cli` で調べても、セッション内の `@dsh-fish/hub` プラグインから検索しても、出力される計画はまったく同じです。

実際に Bundle を試すときは、次の 3 コマンドだけで完結します。

```bash
npx @dsh-fish/cli show <artifact-id>
npx @dsh-fish/cli add <artifact-id> --profile web
dsh --profile web
```

なぜ `show` と `add` を分けているのでしょうか？サードパーティのプラグインコードは、あなた自身のユーザー権限で動作するからです。とくに Git リポジトリ由来のパッケージがビルドスクリプトを要求する場合、そのスクリプトはエージェントのサンドボックス外で実行されます。インストール計画はそれを事前に明示し、`--allow-build-scripts` を明示的に渡さない限りビルドスクリプトを実行しません。

## 「すべてがプラグイン」なら、コアは何を守っているのか？

ここで自然な疑問が湧くはずです。ツールもモデルも UI もすべてプラグインなら、システム全体の秩序はどこで保たれているのでしょうか？

答えは、すべてのセッションで共通して守られる 4 つの境界にあります。

1. **追記専用のセッションログと単一プロセスロック。** 会話やツール実行の履歴は追記専用ログ（`session.v4.jsonl.zstd`）に記録され、`SessionHandle` によって同時に 1 つのプロセスしか書き込めないよう保護されます。
2. **明示的に選ばれたワークスペース。** エージェントはあなたが渡したディレクトリの中だけで作業します。Web UI ではワークスペースを選ぶまで入力欄がロックされます。
3. **名前付きの権限プリセット。** セッションはデフォルトで `workspace-write` 権限で始まります。個別に承認するか `danger-full-access` に切り替えない限り、プラグインのツールもこの境界に従います。
4. **ローカルに留まる API キー。** 認証情報は `$DSH_HOME/.credentials.yaml` や環境変数に保存され、`dsh.fish` に送信されることは一切ありません。

## ランタイムとカタログの役割分担

この境界を押さえておくと、2 つのサイトの目的がはっきりと分かります。

- **DeepSeek Harness（`dsh`）** は Cordis 上でプラグインを合成してエージェントを動かすランタイムです。公式ガイドは [deepseek-harness.github.io](https://deepseek-harness.github.io/deepseek-harness/) にあります。
- **`dsh.fish`** は 4 種類の構成単位（`bundle`、`skill`、`agent-preset`、`profile`）を探すためのカタログであり、インストール計画のリゾルバーです。パッケージの公開方法やスコアの算出基準は[製品ドキュメント](/docs)で解説しています。

このカタログでプラグインを見かけたら、まず「これは自分の Profile のどのレイヤーを変えるものか？」と考えてみてください。ブラックボックスの拡張機能ではなく、Profile の合成として捉えられるようになれば、DeepSeek Harness を自在に組み立てられるようになります。
