Imagine you install an extension into your favorite code editor, and it quietly breaks your terminal or hijacks your model settings. When you try to debug it, you realize the editor is a giant black box and extensions are bolted onto the outside with duct tape.

Now imagine a different design. What if the application itself had almost nothing inside its core? What if the chat window, the bash tool, the model connection, and even the agent loop were all loaded the exact same way as a third-party extension?

That is what [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) (`dsh`) means when its README opens with a four-word premise: **everything is a plugin**. That sentence is not a marketing slogan for a marketplace. It is an architectural rule powered by [Cordis](https://github.com/cordiverse/cordis) (described in the paper [_A Programming Paradigm for Spatiotemporal Composability_](https://arxiv.org/abs/2608.25512)).

Once you see how that rule works on disk, both DeepSeek Harness and this catalog (`dsh.fish`) suddenly click into place. Let us walk from the folder on your machine to the running agent session.

## A profile is the unit that boots

Before we talk about plugins, let us look at what actually happens when you type `npx @deepseek-ai/dsh web` in your terminal.

Where does the agent store its state? By default, DeepSeek Harness creates a home directory at `~/.dsh` (or whatever path you set in `$DSH_HOME`). Inside that folder sits a subdirectory called `profiles/`.

Think of a **profile** (`$DSH_HOME/profiles/<name>`) as a self-contained recipe for one version of your agent. It holds the npm packages and the configuration patches (`cordis.patch.yml`) that define which tools, models, and UI panels exist when the process starts.

When you launch `dsh`, you are always booting a named profile:

- `dsh web` boots the `web` profile (the browser interface on `http://127.0.0.1:3080`).
- `dsh --profile headless` boots a one-shot CLI runner with no web server.
- `dsh --profile sdk` and `dsh --profile acp` boot JSON-RPC and Agent Client Protocol servers for external programs.

There is no hidden back door that loads a secret built-in stack. Every entry point starts from a profile. That is why you cannot simply "install a plugin into DeepSeek Harness" in the abstract. Writing a plugin without naming a profile would be writing it into nowhere.

## Four building blocks, from simplest to fullest

If a profile is the recipe that boots, what are the ingredients you can put inside it?

If you browse `dsh.fish`, you will notice there are only four artifact kinds. We did not invent these categories for our database. They are the exact four load surfaces that DeepSeek Harness knows how to read:

| Kind         | Start here if you want to...                                      | How DeepSeek Harness loads it                                                                 |
| ------------ | ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| **Skill**        | Teach the model a repeatable workflow in plain Markdown           | Saved under `$DSH_HOME/skills/<name>/SKILL.md` and read by the model on demand                |
| **Agent preset** | Define a specialized persona, prompt prefix/suffix, and toolset   | Configured via `agent.cordis.yml` (and packaged as a bundle in newer Harness releases)        |
| **Bundle**       | Add new tools, UI panels, model adapters, or runtime hooks in code | An npm package with `dsh.bundle` in `package.json`, installed via `dsh plugin add`            |
| **Profile**      | Share an entire ready-to-run stack of bundles with your team      | An ordered list of bundles (`dsh.profile.bundles`) applied on top of `@deepseek-ai/dsh-base`  |

Notice what is missing from that table. Earlier drafts of this catalog had entries for `mcp-server` and `hook-bridge`. We retired both and redirected their URLs with `301`s to `/browse`. Why? Because the harness never had a standalone load slot with those names. An MCP server or a hook is delivered *inside* a Bundle or a Profile. A catalog that advertises artifact types the runtime cannot actually load only confuses newcomers.

## Why installing is a readable plan, not a blind script

In many ecosystems, installing an extension means copying a `curl | bash` one-liner and hoping for the best. Because DeepSeek Harness composes profiles from multiple layers, we took a different approach on `dsh.fish`.

Whether you look at a plugin on the website, query it from the terminal with `npx @dsh-fish/cli`, or search for it inside a live chat using `@dsh-fish/hub`, you get the exact same **install plan**.

You can try this three-step workflow in your own terminal whenever you evaluate a bundle:

```bash
npx @dsh-fish/cli show <artifact-id>
npx @dsh-fish/cli add <artifact-id> --profile web
dsh --profile web
```

Why separate `show` from `add`? Because third-party code runs with your user privileges. If a git-sourced package needs to run a post-install build script, that script executes outside the agent's tool sandbox. The install plan surfaces that requirement up front and refuses to run build scripts unless you explicitly pass `--allow-build-scripts`.

## If everything is a plugin, what does the core still guard?

At this point, a reasonable question comes up: if tools, models, and UI panels are all plugins, what keeps the system coherent?

Even in a plugin-first runtime, four boundaries remain constant across every session:

1. **The session log is append-only.** Every prompt, tool call, and response is recorded as a durable event sequence (`session.v4.jsonl.zstd`), guarded by a single-process lock (`SessionHandle`) so two processes never corrupt the same history.
2. **The workspace is an explicit directory.** The agent only operates inside the project folder you hand it, and the Web UI composer stays locked until you pick one.
3. **Permissions are named presets.** A new session starts in `workspace-write` mode by default. Plugins operate within that boundary unless you approve an action or deliberately switch to `danger-full-access`.
4. **Your API keys stay on your machine.** Credentials live in `$DSH_HOME/.credentials.yaml` or your environment variables. `dsh.fish` never sees your keys or your model traffic.

## Where the runtime ends and the catalog begins

Keeping that boundary clear makes both tools easier to understand:

- **DeepSeek Harness (`dsh`)** is the runtime that composes plugins via Cordis and runs your agent sessions. Its official documentation lives at [deepseek-harness.github.io](https://deepseek-harness.github.io/deepseek-harness/).
- **`dsh.fish`** is the public catalog and install-plan resolver for the four loadable kinds (`bundle`, `skill`, `agent-preset`, `profile`). Our [product docs](/docs) explain how to package those artifacts and how our quality and maintenance scores are calculated.

Whenever you look at a plugin on this site, ask one question: *which part of my profile composition is this changing?* Once you think in profiles and layers instead of black-box extensions, you are in full control of your agent.
